# 云平台人力产能工作台

替代原「云平台-YYYY年M月人力情况」Excel 的人力产能核算工具。支持多人实时协同填报。

## 三种运行方式

同一份代码，不用改任何文件，区别只在启动方式。详细步骤见 **[部署指南.md](部署指南.md)**。

### 实时协同（多人一起填）

```
node server.js
```

启动后控制台打印内网访问地址，发给各组主管即可。所有人填同一份数据，**任何人提交后其他人页面自动刷新**。数据存 `data/state.json`，每次变更归档到 `data/history/`。只需 Node.js，无 npm 依赖。

这条命令在你自己电脑上跑（临时共享）和在内网服务器上跑（长期使用）完全一样，服务器部署只是额外配个开机自启，见部署指南第 4 步。

### 单机模式（自己核算用）

双击 `index.html`。数据存浏览器 localStorage，靠导出/导入 JSON 传递 —— 看不到别人填的内容。顶栏显示「单机模式」标识。

### 可选配置

三个环境变量，**都不填就是默认值**，本地使用无需设置：

| 变量 | 默认 | 说明 |
|---|---|---|
| `PORT` | 8770 | 监听端口，也可用 `node server.js 9000` |
| `DATA_DIR` | `./data` | 数据目录，部署时建议指向独立路径 |
| `ACCESS_TOKEN` | 空（不校验） | 访问口令，设置后链接需带 `?token=` |

## 使用流程

1. **版本周期** — 填候选方案的封版/上线时间、工作日与周六天数，勾选「采用」。开发周期 = 工作日 + 周六。
2. **人头数填报** — 各组填正式与外包人数，支持 0.5 小数。可投入迭代人数 = 正式 + 外包。
3. **专项锁定人力** — 登记被专项占用的人力，仅作核对，不自动扣减。
4. **工时数据导入** — 上传原始导出，CSV / xlsx 都支持，自动识别文件类型。**重新导入即整份覆盖**，不保留上一次的数据。
5. **迭代口径** — 勾选本期迭代。**不勾则所有工时为 0。** 每次导入后清单按新文件重建、勾选清空，需重新勾选。
6. **偏差分析** — 出各组工作量/产能/偏差、口径对账、两张工作量汇总表。

## 停止服务与数据安全

**怎么停**：在运行 `node server.js` 的窗口按 `Ctrl+C`。服务会先通知所有在线页面再退出。

**停了之后别人怎么办**：页面顶部立刻出现橙色横幅提示「服务已停止，填写只存本机」，他们可以继续填。服务重启后页面自动重连，把断连期间的填写补交上去。

**多人在断连期间都填了会不会互相覆盖**：不会。恢复时按组、按条目逐项合并——A 填的组和 B 填的组都保留。只有两人改了同一格才会在顶部黄条列出「请核对」，且默认保留你自己的值，两边内容都不丢。

**关服期间能关浏览器吗**：能，暂存在本机浏览器里，下次打开同一浏览器仍会补交。但别清缓存、别换浏览器、别用无痕窗口。稳妥起见可以点横幅上的「导出 JSON 备份」。

**数据存哪**：`data/state.json`。每次变更自动归档到 `data/history/`，文件名含版本号。`state.json` 万一损坏，服务会自动回退到最近一个可用快照。

## 数据源说明（重要）

只需导入**两个**文件：

| 文件 | 作用 | 是否必需 |
|---|---|---|
| 阳光云迭代工作量统计 | 各组工时总计，**产能偏差的唯一权威口径** | 必需 |
| 月底版本项目人力看板 | 产线维度分布，仅用于分类汇总表 | 可选 |

**「阳光云迭代中后台工作量统计」不要导入。** 它和「阳光云迭代工作量统计」是同一份数据的两个导出视图 —— 实测 737 行键完全一致，仅 1 处数值差异（后端开发-平台/7月C版本：云表 172.5、中后台表 170.5）。两表相加会让中后台工时翻倍。中台各组的工时本就挂在 `中后台-2026年M月迭代` 这个迭代下，勾选该迭代即可完整取到。

阳光云版本通常需同时勾选 `阳光云2026-M月C版本迭代` + `中后台-2026年M月迭代`。跨月合并时同时勾选两个月的迭代。

## 取数口径

- 测试部-应用软件测试-云服务取「预估故事点」，其余各组取「故事点」
- 团队名大小写自动归一（`WEB开发` / `Web开发` 视为同一组）
- 全零行自动跳过（原始导出中占多数）
- **ECO 团队自身的组**（APP开发-ECO、后端开发-ECO 等）不计入核算主体；**分类维度的 ECO** 是阳光云团队投在 ECO 任务上的工时，仍然计入。两者不冲突。
- 站控、嵌入式、工具开发部等非阳光云团队静默忽略，不报未识别告警

## 组织架构调整

只改 `config.js`：

- `TEAMS` — 核算主体各组。`key` 须与导出的「所在团队」一致（大小写不敏感），`source` 取 `story` 或 `est`
- `IGNORED_TEAM_PATTERNS` — 非核算主体，前缀匹配，静默忽略
- `PRODUCT_LINES` / `OTHER_CATEGORIES` — 分类归属
- `DEVIATION_TOLERANCE` — 正常偏差阈值，默认 ±10%
- `RECONCILE_TOLERANCE` — 对账告警阈值，默认 2 人天

出现不在任何名单中的团队名或分类值时，第④页会红字列出并说明其工时未被计入 —— 这是刻意的显式失败，避免像 Excel 那样静默算成 0。

## 已修正的原表问题

1. **`规划与产能分析!B30` 是硬编码 293.1**，不是公式。同列其他行都是 `=D16` 形式引用，唯独这行被字面值覆盖过，长期少算后端开发-阳光云的工作量。
2. **团队名大小写不一致** — 导出写 `WEB开发-阳光云`，汇总表头写 `Web开发-阳光云`。Excel 的 SUMIFS 不区分大小写所以没暴露。
3. **迭代维度缺失** — 原表按手工筛选后的数据算，原始导出含 116 个迭代、87 个团队，必须显式按迭代筛选。

## 已知数据质量问题（工作台能暴露但修不了）

- **「智慧能源产品中心」占比约 67%**（1831.75 / 2781.3 人天）。这是部门级兜底分类而非真实产线，占比这么高说明大量任务没打产线标签。产线维度的分析价值受此限制。
- 总计表与看板存在 0.5~1.5 人天的零星差异，来自两份导出的时间差。工作台以总计表为准做偏差计算，并在第⑥页列出超阈值的差异供核对。

## 安全说明

`server.js` **没有账号体系**，只有可选的单一访问口令（`ACCESS_TOKEN`）。能访问端口的人都可读写全部数据，没有按组隔离权限。仅适合内网可信网络，不要暴露到公网。涉及人力编制数据，部署到服务器时建议至少启用口令。
