# Codex 交付与推送规则

适用目录：`E:\PMWork\Project Materials\iSolarCloudProject\迭代版本\iSolarCloudProjectManage`

## 基本原则

- 不直接向 `main` 推送。
- 不做 `git reset`、`git checkout --`、强推、数据库迁移、seed/reset 等可能覆盖现有工作区或平台数据的操作。
- 不覆盖 Kiro 或用户已经修改的文件；如同一文件已有未确认改动，先读取并基于现状追加修改。
- 涉及运行态数据、生产数据、迁移脚本、部署脚本时，先说明风险，再执行。
- 代码提交使用独立远程分支，命名建议：`codex/<需求名>-YYYYMMDD`。

## 推送前只读确认

每次推送前先做只读检查：

- `git status -sb`：确认当前分支、ahead/behind、未提交文件。
- `git remote -v`：确认远端仓库。
- 仓库文件清单：确认是否存在 CI/CD 或自动部署配置。
- 差异范围：区分代码文件、文档文件、运行态数据文件。
- 部署说明：核对是否要求排除 `data/`。

## 提交范围规则

- 优先只 stage 本次明确新增或修改的代码/文档。
- 不使用 `git add .`。
- `data/` 下的 `state.json`、`history/`、`archive/`、`audit-log.json` 默认视为运行态数据，不随代码提交，除非用户明确要求。
- `node_modules/` 不提交。
- Excel 原始材料和业务敏感数据文件不新增提交，除非用户明确指定。

## 分支与远端规则

- 独立创建本地分支，例如：`codex/archive-handoff-20260819`。
- 推送命令使用：`git push -u origin <branch>`。
- 不合并 PR，不打 tag，不触发部署动作。
- 若远端 CI/CD 对所有分支自动部署，需在最终回复中明确提示用户检查远端流水线。

## 交接文档规则

每次较大需求或跨工具协作时，同步生成或更新交接文档，至少包含：

- 需求理解与目标。
- 当前仓库状态与分支基线。
- 已改动或将改动文件清单。
- 数据风险和禁止操作。
- 验证命令与结果。
- Kiro 可直接执行的提示词。
- 未完成项和下一步建议。

## 进度透明规则

- 执行阶段性操作前先说明将要读、改或推什么。
- 长任务每约 30 秒同步一次进展。
- 若能获取到会话预算或状态，则同步当前状态；若无法获取实时金额，以 OpenAI Usage Dashboard / Billing / Costs API 为准。
