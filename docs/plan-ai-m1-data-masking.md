# 数据脱敏规范（M1 发布版）

> 定位：本文是 M1 的**脱敏落地口径**，也是 M2「数据自动流入」和 M3「Agent/AI」的**前置红线**。
> 方向以 `plan-ai-master.md` 第 4.5 节为准，本文把它从「三级框架」升级为「字段级可执行规则」。
>
> 版本：v1 ｜ 发布：2026-09-21 ｜ 数据基线：`main` @ M1 完成态
> 读者：执行方（SGAI+/Claude Code）、后续接 M2 适配器与 Skill 的开发者。
>
> **一句话**：脱敏不是「一刀切删除」，是**分级 + 按场景取用 + AI 侧二次校验**。
> 平台内给登录用户看的数据，权限已经限定了可见范围，不重复脱敏；
> 真正要守的是**数据流出平台的边界**（进 AI、进备份、进日志、跨系统传输）。

---

## 0. 红线（不可逾越）

1. **L3 永不进云端 AI**：代码原文、核心算法、商务合同、成本明细，任何情况下不喂给 SGAI+/外部模型；代码只取统计特征（PR 数 / 合并率 / 评审耗时）。
2. **真实工时绝对值不流出**：喂给 AI 的是「偏差百分比 / 区间 / 聚合值」，不是「123 小时」。
3. **真实姓名可保留审计能力，但不可反查真人**：用假名，假名映射表本身按 L3 加密管理（见第 6 节）。
4. **凭据类字段零外泄**：`users.password_hash`、会话 `token`、钉钉密钥，永不进日志 / 备份明文 / AI / 前端。
5. **从严默认**：新增字段未定级前，一律按 L3 处理，review 后方可降级。

---

## 1. 数据分级（L1 / L2 / L3）

| 级别 | 定义 | 典型字段 | 处理要求 |
|---|---|---|---|
| **L1 公开** | 可在团队内公开、甚至对外的信息 | 项目代号、里程碑节点、迭代排期（去掉工时后）、公开状态 | 正常使用；进 AI 前仍走输出校验 |
| **L2 内部** | 内部进度与人力信息，泄露影响管理判断但非致命 | 工时/工作量、内部进度、偏差数据、部门归属、成员角色、TB 内部 ID | 仅登录用户按权限可见；进 AI 时**聚合化/百分比化**；不出平台明文 |
| **L3 机密** | 泄露即事故 | 代码原文、核心算法、商务合同、成本明细、真实姓名↔假名映射表、`password_hash`、钉钉 userId、密钥 | 不进云端 AI；仅本地/私有化；映射表加密；凭据零外泄 |

> 分级判定原则：**就高不就低**。一个字段同时含 L2 工时和 L3 成本时，按 L3 处理。

## 2. 字段级脱敏规则（核心对照表）

下表对照本仓库真实字段（`data/iteration/state.json` 业务字段 + `db.js` 系统库表结构）。
「脱敏后形态」指**数据流出平台**（进 AI / 跨系统 / 备份 / 日志）时应呈现的样子；
平台内给已授权用户看时保持原样。

| 字段（真实来源） | 级别 | 脱敏手段 | 流出时的形态 | 说明 |
|---|---|---|---|---|
| 真实姓名（`state.json.updatedBy`、`audit_log.user_name`、成员/负责人） | L3 | 假名化 | `U_1001` / 角色称谓（`后端开发`） | 保留「谁干的」审计关联，但不可反查真人（映射表见第 6 节） |
| 工时/工作量（`weight`、`workload`、人天、`deviationOverrides.*.workload`） | L2 | 聚合化 / 区间化 / 百分比化 | 「偏差 +12%」/「80–100 人天」/「占比 35%」 | 喂 AI 用偏差百分比，绝不喂绝对小时数 |
| 项目/迭代名（`iterations[].name`、`tbSprintMap` 值） | L1↔L2 | 项目代号映射 | `PRJ-CLOUD-A` / `SPR-2026-09` | 代号保留跨项目关联性，便于 Agent 跨项目召回 |
| 部门名（`deviationOverrides` 键、组织结构） | L2 | 保留 / 代号 | 视场景；进 AI 可用代号 | 小团队场景部门名区分度低，优先代号 |
| TB 内部 ID（`tbBoardSprints.*.sid`、sprint id） | L3 | 平台内映射 | 仅平台内部引用，不出平台 | 第三方系统句柄，泄露可被反查 |
| 代码内容 / PR diff | L3 | 统计特征化 | PR 数、合并率、评审耗时、改动文件数 | 只取统计，不传原文 |
| 成本 / 商务 / 合同 | L3 | 禁止 | 不进平台 AI；平台内仅授权角色 | 红线第 1 条 |
| `users.password_hash` | L3 | 禁止外泄 | 永不出存储/日志/前端/AI | scrypt 加盐哈希，本就不应明文 |
| `users.dingtalk_id` | L3 | 平台内映射 | 仅登录流程内部使用 | M2 扫码登录才启用，当前预留 |
| 会话 `sessions.token` | L3 | 禁止外泄 | HttpOnly，不出日志 | 改 token 即请求被拒（已实现） |
| `audit_log.details` | L2 | 输出前脱敏 | 剔除其中内嵌的姓名/工时绝对值 | 详情字段易夹带，入库前过滤 |

## 3. 四种脱敏手段（怎么脱）

| 手段 | 适用 | 效果 | 注意 |
|---|---|---|---|
| **假名化** | 人名 | 保留审计关联 + 跨项目一致性，不可反查真人 | 假名须**稳定**（同一人跨项目同一假名）；映射表 L3 加密 |
| **聚合化 / 区间化** | 工时、人数 | 消除绝对值敏感度 | 区间宽度按场景定（如 10 人天一档）；样本过小时只给聚合不给个体 |
| **百分比化 / 归一化** | 工时偏差、产能 | 天然脱敏且对 AI 更有用 | 「偏差 +12%」比「123 小时」既安全又是 Agent 需要的信号 |
| **统计特征化** | 代码 / PR | 满足进度判断，不留原文 | 只保留 PR 数、合并率、评审耗时、改动文件数等维度 |

> 删除（掩码/置空）只在字段确定无业务价值时使用；**默认优先假名/聚合，保留可用性**。

## 4. 场景矩阵（哪个边界脱到什么程度）

| 场景 | L1 | L2 | L3 | 说明 |
|---|---|---|---|---|
| 平台内展示（已登录用户） | 明文 | 明文（权限已限可见范围） | 仅授权角色明文 | 权限矩阵（M1 步骤 3）已把可见范围卡死，不重复脱敏 |
| 备份文件 | 明文 | 明文 | **加密** | 备份与源同级；L3 映射表/凭据单独加密（见第 6 节） |
| 内部系统间传输（钉钉 / Git 回流平台） | 明文 | 明文（内网） | **禁止** | 跨系统只传 L1/L2；L3 不跨边界 |
| 喂给 AI（SGAI+） | 明文 | **聚合/百分比后** | **禁止** | Skill 输入模板固化脱敏约束；代码只取统计特征 |
| AI 输出回写平台 | 校验 | 校验 | **拦截** | 输出命中真实姓名/L3 关键词 → 拒绝入库 + 写审计（见第 5 节） |
| 审计 / 日志 | 明文 | 脱敏 | 假名 | 日志里的人名一律假名；token/哈希零落盘 |

## 5. AI 特化（SGAI+ 集成边界）

1. **输入侧**：每个 Skill 的输入模板必须写死「脱敏」约束（通用五要素里的「约束」项已含此项）。
   喂给 Agent 的数据 = 脱敏后的 L1 + 聚合化的 L2；**绝不喂 L3，绝不喂工时绝对值**。
2. **输出侧二次校验**：AI 产出入库前过一道脱敏校验器——
   - 命中**真实姓名词表**（来自用户/成员名单）→ 替换为假名或告警；
   - 命中 **L3 关键词**（成本金额、合同号、代码片段特征）→ 拒绝入库；
   - 校验不通过 → 写 `audit_log`（`action='ai_mask_blocked'`），不静默丢弃。
3. **AI 行为可溯源**：`audit_log.ai_triggered`（该操作由 AI 触发）/ `ai_adopted`（AI 建议是否被采纳）已建表，
   M3 起 Agent 自主执行的每一次落库都打标，出了事追得到「哪次 AI、哪条建议、谁采纳」。
4. **代码只取统计特征**：M2 接 Git 后，喂 AI 的是 PR/评审的统计维度，不传 diff 原文（红线第 1 条）。

---

## 6. 假名映射表管理（怎么做到「能审计、不能反查」）

- **假名规则**：`U_` + 稳定标识（建议用工号哈希前缀），同一人跨项目、跨模块同一假名，保证审计连续性。
- **映射表 = L3**：`假名 ↔ 真人` 映射单独建表，**AES 加密存储**，密钥不落代码库、不落备份明文。
- **反查权限**：仅 `admin` 可解密反查，且**每次反查写审计**（`action='pseudonym_resolve'`，记录人/时间/查了谁），反查行为本身可追责。
- **落点**：M1 先在规范层约定；`pseudonyms` 表与加密实现随 M2 首个含人名的 Skill 上线时落地（不阻塞 M1 验收）。

## 7. M2 接入检查清单（数据流入前的脱敏卡点）

- [ ] 每个数据适配器（钉钉 / Git / 各团队工作台）入口挂**脱敏过滤器**，L3 字段在入口即拦截，不落入平台。
- [ ] 每个 Skill 的输入模板固化脱敏约束（第 5 节），输出侧挂二次校验器。
- [ ] L3 字段清单 review 一遍（代码原文 / 成本 / 合同 / `password_hash` / `dingtalk_id` / TB sid / 映射表）。
- [ ] 备份流程对 L3（映射表、凭据）单独加密（第 4 节备份行）。
- [ ] 审计 / 日志管道对人名统一假名化、对 token/哈希零落盘。
- [ ] 新增字段默认 L3，降级走 review（第 8 节）。

---

## 8. 变更管理

- **就高默认**：任何新增字段未定级前按 L3 处理。
- **版本化**：本规范改动升版本号，重大口径变化在 `plan-ai-master.md` 同步一句。
- **触发 review**：接入新数据源、新增 Skill、或发生一次疑似泄露时，重新过一遍第 2 节字段表。

---

## 附：与 M1 其它步骤的关系

- 脱敏**依赖** M1 的身份/权限（步骤 1/2/3）：没有可信身份，「谁能反查假名」「谁能看 L3」无从谈起。
- 脱敏**不依赖**前端登录页是否打开：平台内展示层的可见范围由权限矩阵管，脱敏管的是**流出边界**。
- 本规范是文档活，**不阻塞 M1 代码验收**，但 M2 接数据前必须先落地第 7 节卡点。
