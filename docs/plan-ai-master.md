## 1. 目标与验收标准（唯一版本）

### 1.1 终局愿景

一个能自主运转的 AI PMO 体系：数据自动从各来源流入、AI 主动识别风险与偏差、人只在关键节点做判断。AI 可以自主执行，但不能自主负责。

### 1.2 可验收的阶段目标

| # | 目标 | 验收标准（可量化） |
|---|---|---|
| A | 可发布、可多人协作 | 两个人同时登录，看到各自视图，改的数据互不覆盖 |
| B | 与钉钉等平台打通获取数据 | 一周不手动录数据，平台进度仍在更新 |
| C | 支持 AI 能力 | AI 生成的周报"改一改就能发"，而非"全部重写" |
| D | 知识库沉淀 | 历史经验在风险识别时被自动召回，而非躺在文件夹里 |
| E | 治理完备 | 数据分级脱敏、权限矩阵、AI 行为日志、决策溯源、偏差告警全部生效 |

**唯一诚实的指标：采纳率**（AI 产出被直接采纳/略改采纳的比例）。

## 2. 现状盘点（基于代码勘察，非估计）

### 2.1 已具备（应用层）

| 模块 | 说明 |
|---|---|
| iteration | 迭代人力/工时统计 + 偏差核算，已与 TB 打通 |
| plan | 项目计划 / WBS / 里程碑 / 资源 / 甘特 / 高管视图（AI 入口预留） |
| project / budget / csenergy / token / dashboard / tb | 项目跟踪 / 预算 / 项目线 / 令牌 / 跨模块聚合 / TB 同步 |

平台骨架：`server.js` + `module-loader.js`（模块自动发现）+ `router.js` + `platform.js`。**模块化架构、SSE 实时协同、乐观锁（409）、审计日志、访问口令已具备。**

### 2.2 地基四个硬缺口（M1 必须解决）

| # | 缺口 | 现状证据 | 影响 |
|---|---|---|---|
| 1 | 没有真正的数据库 | 各模块 `fs.writeFileSync` 写独立 JSON | 无法按人/按条件查询；无法追加写与长期留存；并发写靠乐观锁硬扛（乐观锁只解决并发，不解决身份） |
| 2 | 身份是假的 | `platform.js` `whoami()` 读浏览器 localStorage 字符串 | 任何人改 localStorage 就是别人，所有"谁改的"记录不可信 |
| 3 | 权限只有口令/无口令 | 全平台一个 `ACCESS_TOKEN` | 无法表达"PM 能改计划、研发只能看" |
| 4 | 审计日志会丢 | `audit.js` 全量重写且只保留最近 200 条 | 无法支撑 Harness 审计层长期留存 |

> **缺口 1 的「数据量大全量读写」不是换数据库的理由。** 实测 280KB 的 `state.json`
> 全量读+改+写约 7ms，涨到 5MB 也还是几十毫秒级。上数据库的真实理由只有两个：
> **「查询」和「留痕」**——这两件事 JSON 做不了。详见 `plan-ai-m1-foundation.md` 第二节。

**逻辑链：身份是假的 → 权限没意义 → 审计只是自娱自乐 → 不敢让 Agent 自主执行。所以 M1 不可跳过。**

## 3. 目标架构（六层）

```
┌──────────────────────────────────────────────────────────────┐
│ ⑥ AI 层：Skill 库 + Agent 矩阵（项目/项目集/组合三层）          │
│   Harness 治理壳：权限矩阵 · 审计日志 · 人机确认点 · 数据分级     │
├──────────────────────────────────────────────────────────────┤
│ ⑤ 应用层（现有看板升级）：账号 + 角色 + 分权视图                │
│   迭代工时 · 项目计划WBS · 年度跟踪 · 预算 · 驾驶舱 · 知识库     │
├──────────────────────────────────────────────────────────────┤
│ ④ 知识层：原始库 → AI 抽取 → 结构化库（风险案例/SOP/LL）→ 决策层 │
│   被 Agent 自动查询的服务，不是"页面"                          │
├──────────────────────────────────────────────────────────────┤
│ ③ 数据接入层：adapter 模式 + 统一数据契约（L1/L2/L3 置信度分级） │
│   Teambition · Git PR/Commit · 钉钉 · 各团队工作台 API/导出     │
├──────────────────────────────────────────────────────────────┤
│ ② 主数据层：项目注册表（项目名/成员/文档空间/周会文档/IM群/工具） │
│   所有 Agent 冷启的唯一锚点，先于场景扩展                       │
├──────────────────────────────────────────────────────────────┤
│ ① 底座层：数据库（SQLite）· 真实身份认证 · 权限体系 · 部署上线   │
└──────────────────────────────────────────────────────────────┘
```

**贯穿全部六层的一条铁律：AI 的输出必须落在"一个需要人点确认的待办"里，而不是"一堆需要人去读的报告"里。"今日待确认"入口是整个 AI PMO 的落地形态。**

## 4. 数据打通设计

### 4.1 Teambition（已有，保持）

TB OpenAPI 拉取 + Webhook 订阅 + 每日全量对账。迭代工时与偏差核算已打通，保持。

### 4.2 统一数据契约（先于逐个接入）

统一字段：task_id/external_system、title、status/status_category、assignee/reporter（映射统一工号）、project_id/iteration_id、start/due/actual_end、progress/story_points/workload、updated_at。

**adapter 模式，不点对点硬编码**：每个来源一个 adapter（Git 一个、钉钉一个、团队工作台 API 一个、标准模板导出兜底一个），全部加在平台这一侧，团队无需改任何东西。团队接入成本 = 填一张契约表。

### 4.3 Git PR → 任务 → 项目：映射推理（核心机制）

**难点不在拉 PR，在"映射"和"置信度"**。四级匹配：

| 级别 | 匹配方式 | 置信度 | 系统动作 |
|---|---|---|---|
| L1 显式关联 | PR 出现 `#<任务号>` 或分支名含任务号 | 高 | 自动更新任务为"有实质进展"，记入变更日志 |
| L2 语义关联 | 标题/分支名与任务名相似度匹配 | 中 | 生成**待确认建议**，人点"是/否" |
| L3 仓库关联 | 只知道动了哪个仓库/模块 | 低 | 只更新项目活跃度，不碰任何任务 |
| L4 无法关联 | 没匹配上 | 无 | 只进原始日志，供追溯 |

**L2 的确认动作在训练映射规则**：点得多了 L2 自然升级为 L1，越用越准。

**推理原则（克制）**：PR 数据不直接覆盖手写完成度，而是**佐证计划是否可信**——"有佐证 → 安静；没佐证 → 报警"。不硬算"完成了 73%"，因为代码合并不等于联调、测试、验收通过。

采集信号：PR 标题、分支名、PR 正文（`Closes #142`）、变更文件路径、提交时间线（流转效率/静默）、评审/合并状态。

### 4.4 钉钉打通（M2）

| 能力 | 方式 | 场景 |
|---|---|---|
| 钉钉文档 | 开放 API 读写 | 章程/周报/复盘自动写入共享文档空间 |
| 会议 AI 听记 | 纪要读取 | 会后自动抽取 Action，写入看板并@负责人 |
| 群机器人 | 机器人 Webhook/互动卡片 | 每日进度播报、风险预警、催更、周报推送 |
| 待办/审批 | 开放 API | AI 建议生成待办、审批流走钉钉 |
| 通讯录 | 组织架构 API | 负责人/干系人自动关联工号部门 |

状态：进行中，等凭据（见 `plan-dingtalk-checklist.md`）。

### 4.5 数据脱敏规范（M1 同步发布）

| 级别 | 定义 | 处理要求 |
|---|---|---|
| L1 公开 | 项目名、里程碑等可对外信息 | 正常使用 |
| L2 内部 | 人力工时、内部进度、偏差数据 | 仅内网访问；姓名打码为工号/角色 |
| L3 机密 | 代码仓库内容、核心算法、商务合同、成本明细 | 不进云端 AI；仅本地/私有化；代码只取统计特征（PR 数/合并率/评审耗时），不传原文；AI 输出二次脱敏校验 |

## 5. 知识库设计（三层）

| 层 | 内容 | 来源 | 给谁用 |
|---|---|---|---|
| 原始层 | 文档/周报/纪要/复盘/立项材料 | 现有材料 + 钉钉文档 | 检索 |
| 结构化层 | 风险案例、LL、SOP、模板 | **AI 从原始层抽取（Skill 的活）** | 喂给 Agent |
| 决策层 | "上次类似情况怎么处理的、结果如何" | 结构化层 + 项目结局回填 | 决策简报 |

**避免变坟墓：三个时刻强制自动调用**——风险识别时（召回历史同类风险+应对+结果）、新项目立项时（推送同类项目踩坑清单）、复盘时（与历史同类对比"这次的问题上次也出现过"）。
**知识库不是页面，是一层被 Agent 自动查询的服务。**

## 6. Prompt 工程

### 6.1 通用五要素：角色 + 上下文（自动注入项目注册表）+ 任务 + 约束（数据范围/脱敏/不许编造）+ 输出格式。

### 6.2 场景矩阵

| 类别 | 典型 Prompt | 频次 | 关键约束要素 |
|---|---|---|---|
| 启动类 | 项目章程生成、干系人登记册 | 每项目 1 次 | 战略目标、组织架构、授权边界 |
| 规划类 | WBS 生成、风险清单、成本估算 | 每阶段 1 次 | 历史数据、资源池、项目约束 |
| 监控类 | 周报生成、偏差分析、健康度评估 | 每周/每迭代 | 实际数据、基线上期对比 |
| 收尾类 | 复盘报告、经验教训提取、归档清单 | 每项目 1 次 | 全过程数据、团队反馈 |

### 6.3 周报 Prompt 模板（范例，可直接用）

```
你是项目经理助理，为[项目名]生成第[X]周周报。
数据来源（已自动拉取，仅基于以下数据，不得编造）：
- 本周任务完成/进行中/延期清单（附 Teambition 数据）
- 本周合并的 Git PR 及关联任务
- 本周人力投入与工时偏差
- 上期遗留事项
任务：1. 总结本周核心进展（≤5 条，每条含数据）2. 列出延期/风险事项及原因
      3. 给出下周计划与需要的支持
约束：脱敏（人员用角色称呼）；延期事项必须给出偏差天数；
输出格式：Markdown 周报模板，含「进展/风险/下周计划/需协调」四节。
```

## 8. Agent 矩阵（人本 / 补强 / 责任）

### 8.1 三条工程铁律（借鉴小红书实践）

1. 原子 Agent 必须自我闭环：要么成功返回结果，要么明确失败返回原因，执行期间不依赖上级再次介入。
2. 复合 Agent 由原子组合，不互相嵌套（防死循环与算力浪费）。
3. 子 Agent 统一返回标准 JSON，由 Master Agent 决策；通知统一走消息通道。

### 8.2 三层矩阵

| 层级 | Agent | 核心能力 | 触发场景 |
|---|---|---|---|
| 项目层 | 文档 Agent | 章程/WBS/周报/复盘自动生成 | 阶段转换、周迭代节点 |
| | 进度 Agent | 自动拉数据、分析偏差、预警延期 | 每日/每周自动运行 |
| | 风险 Agent | 扫描历史模式、识别新风险、跟踪应对状态 | 阶段评审前、重大变更后 |
| | 沟通 Agent | 会议纪要提取、干系人消息推送 | 每次会议后、里程碑达成后 |
| 项目集层 | 依赖分析 Agent | 扫描所有计划，标记关键依赖链 | 周期性 |
| | 资源调度 Agent | 监控资源负荷，提示冲突并建议调配 | 周期性 |
| | 收益跟踪 Agent | 追踪收益实现，对比立项假设，预警偏离 | 周期性 |
| 组合层 | 优先级排序 Agent | 按战略贡献/ROI/风险/紧急度打分排序 | 立项决策时 |
| | 健康度监控 Agent | 汇聚数据生成红黄绿灯仪表盘和异常摘要 | 每日 |
| | 止血分析 Agent | 对问题项目做投入产出再评估，给"继续/暂停/终止"建议 | 问题项目触发 |

### 8.3 多人协同模式：项目专属 BP（1 项目 × N 人 × M Session）

- 每个项目组共享一份动态项目上下文（进展/风险/结论/知识），成员各自独立会话但都从共享上下文取数。
- **项目上下文路由**：识别用户问的是哪个项目，自动绑定该项目的共享上下文。
- **角色感知**：同一问题按角色给不同粒度——管理者看目标达成度与卡点；PM 看全局进展与风险；成员看自己依赖的模块。
- **信息中枢优先**：PMO BP 先是信息中枢，其次才是任务执行者，所有回答有据可查（引用数据源）。

### 8.4 典型闭环（虚拟项目经理）

```
每日自动：各来源拉数据 → 进度 Agent 算偏差 → 风险 Agent 标记异常
→ 自动更新组合级健康度看板 → 只把"红灯"项目推给 PMO 复核
→ 人判断 → 决策回写（五个自动化节点，人只在最后两个节点介入）
```

## 9. Harness 治理工程

### 9.1 约束层

| 机制 | 落地方式 |
|---|---|
| 数据安全分级 | L1/L2/L3 标签贯穿接入→存储→AI 调用→输出全链路；L3 只走本地/私有化 |
| 权限矩阵 | 双层：系统权限（谁能看什么数据）+ AI 能力权限（谁能调哪个 Agent/Skill）。PM 可调文档 Agent，不能调财务 Agent 改预算基准 |
| 合规校验规则 | 法务/财务/采购等敏感领域输出过预设规则自动校验（关键词 + 白名单 + 人工兜底） |
| 动作边界 | 写操作（改任务/发消息/建文档）必须有人的确认；Agent 能力白名单管理 |

### 9.2 审计层

| 机制 | 落地方式 |
|---|---|
| AI 行为日志 | 每次关键操作记录：谁触发、哪个 Agent/Skill、输入摘要、输出摘要、被采纳/拒绝、耗时 |
| 决策溯源 | AI 建议携带"依据引用"，支持一键回溯到原始数据 |
| 偏差告警 | 只读 Agent 试图写数据、越权访问项目、输出含敏感词 → 自动告警 |

### 9.3 进化层

| 机制 | 落地方式 |
|---|---|
| 质量评估回路 | 定期抽查：采纳率、返工率、错误率 → 回灌 Prompt/Skill |
| 评测集机制 | 10+ 类 Case 作为单元测试，升级先跑评测再上线 |
| 规则迭代 | 规则中心可配置化，业务规则/法规/组织变化时快速更新，不写死代码 |
| 能力升级规划 | 半年一代际：只读 Agent → 建议类 → 低风险执行类，逐级放开权限 |

## 10. AI 底座集成：SGAI+ 为主，Kiro 为辅

### 10.1 模型选型（按用途分层，不写死某一家）

| 用途 | 建议 | 理由 |
|---|---|---|
| 编排与复杂推理（大脑） | 能力最强的那一个 | 弱了全盘弱 |
| 公司合规的执行动作（敏感数据/内部通知） | 内部 SGAI+ | 数据不出内网，安全审核好过 |
| 代码 / PR 分析 | 内部 coding agent | 更擅长读代码仓库 |

判断标准：**数据能不能给它、给了它安不安全**。架构要求：模型调用做成可插拔一层，先跑通一个，再换另一个对比。

### 10.2 与 SGAI+ 的三种集成模式

| 模式 | 做法 | 适用阶段 |
|---|---|---|
| A. 看板 + SGAI+ 双轮驱动 | 看板负责数据采集/展示；SGAI+ 负责 AI 分析/定时任务/通知。看板把数据查询封装成可调用工具，SGAI+ 定时任务跑 Skill（周报/偏差/风险），结果回写看板或推钉钉群 | M2-M3 |
| B. 深度嵌入：项目专属 BP | 基于 SGAI+ 会话与角色感知能力，为每个项目组配置共享上下文 + 专属 Agent，钉钉群里即可@Agent 提问/催更/生成周报 | M3+ |
| C. Kiro 辅助 | 只做知识库/资料检索补充，不作主编排引擎 | 全程 |

### 10.3 落地要点

1. Skill 先行：把 12 个 Skill 逐一在 SGAI+ 沉淀为"项目管理 Skill 包"。
2. 定时任务编排：偏差分析（每日）、周报（每周五）、健康度（每周一）、Git 信号（每日）。
3. 项目注册表是锚点（可用钉钉文档起步，再演进为独立小应用）。
4. 每个 Skill 配评测集，迭代跑评测。

## 附：小红书文章 7 条经验（设计依据）

1. 不要等设施齐了才开始，每个阶段用最快能落地的平台，架构跟着场景走。
2. 评测集是 Agent 的单元测试（10+ 类 Case）。
3. 原子 Agent 必须自我闭环。
4. 记忆结构化是更智能的底座（画像/会话历史/知识条目/上下文构建）。
5. 领域 Agent = 领域 Source of Truth。
6. 项目主数据先于场景扩展。
7. AI 时代人人都可以是 Builder：PMO = Builder + PMO。
