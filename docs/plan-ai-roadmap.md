# AI 项目管理新范式 · 落地路线图

> 状态：规划稿 v1 ｜ 2026-09-20
> 定位：把「个人看板」升级为「多人协同 + AI 驱动的 PMO 工作台」的建设地图
> 读者：项目负责人（你）｜ 用途：拍板建设顺序与资源投入

---

## 结论先行

1. **最大风险不是 AI 做不出来，是在单人、手工数据、本地文件的底座上堆 AI Agent** —— 会得到一个「看起来很 AI、实际跑不起来」的演示品。
2. **建设顺序必须是：地基 → 数据自动流入 → 多人协同 → AI**。AI 是最后一块多米诺，不是第一块。
3. **现状与目标之间隔着一道「地基断层」**：平台数据全部是 `fs.writeFileSync` 直接写 JSON 文件、身份是浏览器 localStorage 里一个可随意篡改的字符串、无登录无权限。
   **这道断层不跨过去，后面全是空中楼阁。**

## 一、目标定义

### 1.1 终局愿景

一个能自主运转的 AI PMO 体系：数据自动从各来源流入、AI 主动识别风险与偏差、人只在关键节点做判断。

### 1.2 可验收的阶段目标

| # | 目标 | 验收标准（可量化） |
|---|---|---|
| A | 可发布、可多人协作 | 两个人同时登录，看到各自视图，改的数据互不覆盖 |
| B | 与钉钉等平台打通获取数据 | 一周不手动录数据，平台进度仍在更新 |
| C | 支持 AI 能力 | AI 生成的周报「改一改就能发」，而非「全部重写」 |
| D | 知识库沉淀 | 历史经验在风险识别时被自动召回，而非躺在文件夹里 |

**注意 B 的措辞：「进度仍在更新」不等于「进度自动算准」。** 这是本路线图最重要的一条克制——见第四节。

### 2.2 地基上的四个硬缺口

| # | 缺口 | 现状证据 | 影响 |
|---|---|---|---|
| 1 | **没有真正的数据库** | 每个模块各自 `fs.writeFileSync` 写独立 JSON（`server.js:132`、`budget/routes.js:112`、`csenergy/routes.js:114`、`iteration/routes.js:98`、`plan/routes.js:121`…） | 无法按人/按项目做细粒度查询与权限；并发写靠乐观锁硬扛；数据量一大就全量读写 |
| 2 | **身份是假的** | `platform.js:316` 的 `whoami()` 读的是浏览器 **localStorage** 里的一个字符串，无密码、无校验 | 任何人改一下 localStorage 就是别人。**当前所有「谁改的」记录都不可信** |
| 3 | **权限只有「有口令/无口令」** | `server.js:232` 的 `ACCESS_TOKEN` 是全平台一个口令；`data/platform.json` 只有 `editMode: open` 和空 `whitelist` | 无法表达「PM 能改计划、研发只能看」这类角色差异 |
| 4 | **审计日志会丢** | `audit.js` 每条新日志都全量重写文件，且 **只保留最近 200 条** | 作为「AI 行为可追溯」的底座是不够的（Harness 审计层要求长期留存） |

### 2.3 这些缺口为什么必须先补

**因为你终局要的是「AI 可以自主执行，但不能自主负责」（你原话）。**
「不自主负责」靠什么实现？靠**权限边界 + 审计留痕 + 人机确认点**。
而这三样，全部建立在「系统知道你是谁、能管住你能干什么、能把干过什么记下来」之上。
**身份是假的，权限就没意义；权限没意义，审计就只是自娱自乐；审计不可信，就不敢让 Agent 自主执行。**

│          + 优先级排序/健康度/止血分析（组合层）                  │

│   钉钉文档    ──┼→ 统一数据契约 → 摄入 → 映射推理 → 写入平台      │
│   各团队工作台 ──┤   （L1/L2/L3 置信度分级）                    │
│   TB 任务     ──┘                                             │
├──────────────────────────────────────────────────────────────┤
│ ②b 知识层（与数据层平级）                                       │
│   原始库（文档/周报/复盘）→ AI 抽取 → 结构化库（风险案例/SOP）    │
│                          → 决策层（类似情况怎么处理的、结果如何） │
├──────────────────────────────────────────────────────────────┤

**贯穿全部四层的一条铁律：AI 的输出必须落在「一个需要人点确认的待办」里，而不是「一堆需要人去读的报告」里。**
报告没人看，待办才会被处理。「今日待确认」这个入口，就是整个 AI PMO 的落地形态。

## 四、PR → 任务 → 项目：映射推理设计

这是「从各团队 Git 拿进度」的核心机制。**难点不在拉 PR（那个简单），在「映射」和「置信度」。**

### 4.1 采集层：拉什么

| 信号 | 说明 |
|---|---|
| PR 标题 | 映射的主依据 |
| 分支名 | 常含 issue 号或任务名 |
| PR 正文 | 常写 `Closes #142` |
| 变更文件路径 | 反推动了哪个模块 |
| 提交时间线 | 算流转效率、算静默 |
| 评审/合并状态 | 「已合并」的权重高于「已提交」 |

### 4.2 映射层：四级匹配，每级给一个置信度

| 级别 | 匹配方式 | 置信度 | 系统动作 |
|---|---|---|---|
| **L1 显式关联** | PR 里出现 `#<任务号>`，或分支名含任务号 | **高** | 自动更新该任务为「有实质进展」，记入变更日志 |
| **L2 语义关联** | 标题/分支名与计划里的任务名做相似度匹配 | **中** | 生成一条**待确认建议**，人在平台点「是/否」 |
| **L3 仓库关联** | 只知道动了哪个仓库/模块 | **低** | 只更新项目活跃度，**不碰任何任务** |
| **L4 无法关联** | 什么都没匹配上 | 无 | 只进原始日志，供事后追溯 |

**L2 的确认动作有隐藏价值：你每次点「是/否」，都在训练映射规则。** 点得多了，L2 会自然升级成 L1 —— **这套东西越用越准**。这是它比「人工导入 Excel」强的地方，也是它必须早做、长期做的原因。

### 4.3 推理层：从任务信号到项目进度

**核心原则：PR 数据不直接覆盖你手写的完成度，而是用来「佐证你的计划是否可信」。**

```
任务「WBS模板导出」
  计划完成度：60%（人手工填）
  PR 信号：近 2 周 3 个 PR 合并，L1 关联
    ↓
  推断：该任务有持续开发佐证 → 不报警

  若出现：3 周 0 个 PR，但计划说下周交付
    ↓
  推断：滞后风险 → 标黄，进「进度 Agent」观察清单
```

**为什么不做「算出到底完成了 73%」？** 因为那是算不准的——代码合并不等于功能做完，更不等于联调、测试、验收通过。
**做「有佐证 → 安静；没佐证 → 报警」，比硬算百分比可靠得多，也诚实得多。**

### 4.4 各团队工作台：靠 adapter，不靠点对点硬编码

**要打通，但打通的方式决定了成本是 `N` 还是 `1`：**

- ❌ **点对点硬打通**：A 团队一个拉取器、B 团队一个、C 团队又一个 → **N 个团队 = N 套代码**，团队一改就崩。
- ✅ **adapter 模式 + 统一数据契约**：每一类来源写一个 adapter（Git 一个、钉钉一个、团队工作台 API 一个、标准模板导出兜底一个），**adapter 全部加在平台这一侧**。

**团队不需要改任何东西**（除非它愿意按契约提供 API）。所以「我打开平台就看到最新进展，不用手动导」**完全能实现**——这正是要的效果。

## 五、知识库设计

知识库是整个 AI PMO 里**唯一会「越用越值钱」的资产**。

### 5.1 三层知识

| 层 | 内容 | 从哪来 | 给谁用 |
|---|---|---|---|
| **原始层** | 项目文档、周报、会议纪要、复盘报告、立项材料 | 现有材料 + 钉钉文档 | 检索（人要查历史） |
| **结构化层** | 风险案例、Lessons Learned、SOP、模板 | **AI 从原始层抽取**（这正是 Skill 干的活） | 喂给 Agent（风险识别要历史模式） |
| **决策层** | 「上次类似情况怎么处理的、结果如何」 | 结构化层 + 项目结局回填 | 决策简报、风险建议 |

### 5.2 怎么避免变成「存进去没人看」的坟墓

知识库最大的风险是沦为死档案。**它必须在三个具体时刻被自动调用：**

1. **风险识别时** → 自动检索「历史同类风险 + 当时的应对 + 最终结果」，直接出现在风险清单的「建议」列里；
2. **新项目立项时** → 自动推送「同类项目踩过的坑」清单；
3. **复盘时** → AI 把本次复盘与历史同类项目复盘做对比，指出「这次的问题上次也出现过」。

**一句话：知识库不是一个「页面」，是一层「被 Agent 自动查询的服务」。只有被自动调用，它才有价值。**

## 六、AI 能力设计

### 6.1 Prompt 工程（四类场景）

| 场景 | 典型 Prompt | 频次 | 关键约束要素 |
|---|---|---|---|
| 启动类 | 项目章程生成、干系人登记册 | 每项目 1 次 | 战略目标、组织架构、授权边界 |
| 规划类 | WBS 生成、风险清单、成本估算 | 每阶段 1 次 | 历史数据、资源池、项目约束 |
| 监控类 | 周报生成、偏差分析、健康度评估 | 每周/每迭代 | 实际数据、基线上期对比 |
| 收尾类 | 复盘报告、经验教训提取、归档清单 | 每项目 1 次 | 全过程数据、团队反馈 |

### 6.2 Skill 封装规范（三要素）

每个 Skill 必须有：**输入模板 → 处理逻辑 → 输出规范**。以「项目风险识别器」为例：

```
【Skill 名称】项目风险识别器
【触发条件】新项目进入规划阶段，或已有项目的阶段评审前
【所需输入】
  - 项目基本信息（行业、类型、规模、周期）
  - 历史同类项目的风险清单和复盘报告   ← 来自知识库结构化层
  - 当前项目的 WBS 和关键假设
【处理逻辑】
  1. 基于历史数据提取高频风险模式
  2. 逐项比对当前项目特征，识别匹配风险
  3. 对每个风险按「概率 × 影响」分级
  4. 为高优先级风险生成初步应对建议
【输出规范】
  - 风险清单表（ID、类别、描述、概率、影响、等级、应对策略、责任人）
  - TOP5 风险详细分析（触发条件、预警信号、建议措施）
  - 风险间关联关系图（一个风险触发另一个风险的链路）
```

### 6.3 建议沉淀的 Skill 清单（按优先级）

| # | Skill | 输入 | 输出 | 优先级 |
|---|---|---|---|---|
| 1 | **项目风险识别器** | 项目信息 + 历史风险库 + 当前 WBS | 风险清单 + TOP5 分析 + 关联图 | ⭐ 最高 |
| 2 | **周报生成器** | 本周变更 + 偏差数据 | 结论先行的周报 | ⭐ 最高（每周一次，杠杆最大） |
| 3 | **进度偏差分析器** | 基线 vs 实际 | 「哪个里程碑要延期、根因、建议动作」 | ⭐ 最高 |
| 4 | **依赖链扫描器** | 所有项目计划 | 「谁卡谁」的依赖图 | 中（数据更全后做） |
| 5 | **复盘沉淀器** | 全过程数据 + 团队反馈 | 结构化 Lessons Learned 条目 | 中 |
| 6 | **决策简报生成器** | 异常项目数据 | 「发生了什么/为什么/影响/方案」四段式 | 中 |

**先做 1、2、3**：有现成数据、频率高、见效快。

### 6.4 Agent 矩阵（人本 / 补强 / 责任）

| 层级 | Agent | 核心能力 | 触发场景 |
|---|---|---|---|
| **项目层** | 文档 Agent | 章程/WBS/周报/复盘自动生成 | 阶段转换、周迭代节点 |
| | 进度 Agent | 自动拉数据、分析偏差、预警延期 | 每日/每周自动运行 |
| | 风险 Agent | 扫描历史模式、识别新风险、跟踪应对状态 | 阶段评审前、重大变更后 |
| | 沟通 Agent | 会议纪要提取、干系人消息推送 | 每次会议后、里程碑达成后 |
| **项目集层** | 依赖分析 Agent | 扫描所有计划，标记关键依赖链 | 周期性 |
| | 资源调度 Agent | 监控资源负荷，提示冲突并建议调配 | 周期性 |
| | 收益跟踪 Agent | 追踪收益实现，对比立项假设，预警偏离 | 周期性 |
| **组合层** | 优先级排序 Agent | 按战略贡献/ROI/风险/紧急度打分排序 | 立项决策时 |
| | 健康度监控 Agent | 汇聚数据生成红黄绿灯仪表盘和异常摘要 | 每日 |
| | 止血分析 Agent | 对问题项目做投入产出再评估，给「继续/暂停/终止」建议 | 问题项目触发 |

### 6.5 模型选型：按用途分层，不写死某一家

| 用途 | 建议 | 理由 |
|---|---|---|
| **编排与复杂推理**（Agent 分工、判断、写报告） | 能力最强的那一个 | 这是「大脑」，弱了全盘弱 |
| **公司合规的执行动作**（碰敏感数据、发内部通知） | **内部 SGAI+** | 数据不出内网，安全审核好过 |
| **代码 / PR 分析** | 内部 coding agent | 本来就更擅长读代码仓库 |

**判断标准不是「谁方便」，是「数据能不能给它、给了它安不安全」。**
既然有「核心机密数据必须本地部署或私有化」的硬约束，那么：**凡碰内部数据 → 优先内部方案；碰不到敏感数据的通用推理 → 用能力最强的。**

**架构要求：把「模型调用」做成可插拔的一层，先跑通一个，再换另一个对比，不要在架构里写死。**

## 七、Harness 治理工程

### 7.1 约束层

- **数据安全分级**：公开数据走公有云；内部非敏感数据走企业版；核心机密必须本地部署或私有化。
- **权限矩阵**：分角色分级。**PM 可以调用文档 Agent 生成报告，但不能调用财务 Agent 修改预算基准。**
- **合规校验规则**：涉及法务、财务、采购等敏感领域的 AI 输出，必须经预设规则自动校验。

### 7.2 审计层

- **AI 行为日志**：每次关键操作可追溯——谁触发、做了什么、输出什么、**被采纳还是被拒绝**。
- **决策溯源**：AI 给出建议（比如建议终止某项目）时，必须能回溯到依据了哪些数据、什么推理逻辑。
- **偏差告警**：AI 实际行为偏离预设规则时（比如只该读数据的 Agent 试图改数据），系统自动告警。

### 7.3 进化层

- **质量评估回路**：定期抽查 AI 产出质量（采纳率、返工率、错误率），形成量化反馈。
- **规则迭代机制**：业务规则变化、法规更新、组织调整时，约束规则要能快速更新。
- **能力升级规划**：AI 能力半年一代际，Harness 要有前瞻性——什么时候放开更多权限给 Agent？什么时候引入新 Agent 类型？

## 八、落地路线（三个里程碑）

### M1 · 地基 —— 从「个人工具」到「系统」

**为什么必须第一：** 见 2.3。

| # | 任务 | 现状 | 目标 |
|---|---|---|---|
| 1 | 上数据库 | 各模块 `fs.writeFileSync` 写独立 JSON | SQLite（零依赖、单文件、够用，**不必上 MySQL**） |
| 2 | 真实登录 | `whoami()` 读 localStorage 字符串 | 账号 + 密码，或对接钉钉扫码 |
| 3 | 权限矩阵 | 全平台一个 `ACCESS_TOKEN` | 角色 = PM / 研发 / 只读，控制「能看什么、能改什么、能调哪个 AI」 |
| 4 | 部署 | 仅本机 `node server.js` | 内网服务器 + 启动脚本 + 数据持久化路径 |
| 5 | 审计加厚 | `audit.js` 全量重写 + 只留 200 条 | 追加写 + 长期留存 + 按人/模块可查 |

**验收：** 两个人同时登录、各看各的视图、改的数据互不覆盖。
**注意**：现有乐观锁只解决了「并发写」，**没解决「身份」**——这两件事不是一回事。

### M2 · 数据自动流入

| # | 任务 | 说明 |
|---|---|---|
| 1 | **钉钉打通** | 进行中，等凭据（见 `plan-dingtalk-checklist.md`） |
| 2 | **Git PR adapter** | 先接 1-2 个真实仓库，跑通 **L1/L2/L3 三级映射 + 置信度分级** |
| 3 | **统一数据契约** | 出一份《团队工作台对接规范》给各团队，谁愿意接谁接，不接的走标准模板导出兜底 |
| 4 | **静默告警** | 某任务关联仓库 N 周无 PR 但临近交付 → 告警 |

**验收：** 一周不手动录任何数据，平台上的进度仍在更新。

### M3 · 多人协同 + 知识库 + 首批 AI Skill

| # | 任务 | 说明 |
|---|---|---|
| 1 | 知识库三层落地 | 原始库先跑通，AI 抽取后补 |
| 2 | 首批 3 个 Skill | 风险识别 / 周报生成 / 进度偏差分析 |
| 3 | Harness 治理壳 | 审计日志（扩现有 `audit.js`）+ 人机确认点 + 数据分级 |
| 4 | 「今日待确认」入口 | **所有 AI 输出的统一落地形态** |

**验收：** AI 产出的周报你「改一改就能发」，而非「全部重写」。**采纳率是唯一诚实的指标。**

## 九、怎么用（按角色）

| 角色 | 每天打开平台做什么 |
|---|---|
| **PM（你）** | 打开 → 看「今日待确认」（PR 映射建议 + 风险告警）→ 点几下确认 → 看 AI 生成的周报草稿 → 改完发 |

## 十、风险与克制

| 风险 | 说明 | 应对 |
|---|---|---|
| **在错误的底座上堆 AI** | 最大风险。会得到演示品而非产品 | M1 先行，不可跳过 |
| **过度承诺 AI 准确度** | PR 推不出真实完成度，硬算百分比必然失信 | 只做「佐证/告警」，不做「精算」 |
| **知识库变坟墓** | 存了没人看 | 强制在三个时刻自动调用 |
| **AI 输出没人看** | 报告形式无人处理 | 统一落成「待确认待办」 |
| **团队不配合对接** | 各团队工作台异构 | adapter + 契约，不点对点硬编码；兜底走标准模板 |
| **数据合规** | 核心机密不可外流 | 模型分层：内部数据走内部方案 |
