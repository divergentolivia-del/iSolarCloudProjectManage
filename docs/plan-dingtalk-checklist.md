## 二、必需项（缺一项则 2b 无法开工）

### 1. 应用凭据 —— 放在哪、怎么给

**在钉钉哪里拿：** 钉钉开放平台 → 应用开发 → 企业内部应用 → 你创建的那个应用 → **凭证与基础信息**。

**放到哪：** 本机文件 `data/dingtalk/secret.json`（我没有替你建，因为里面要填你的真实密钥）。
目录下已放好 **`secret.example.json`**，复制成 `secret.json` 后逐项替换即可。

需要四个值：

| 字段 | 是什么 | 注意 |
|---|---|---|
| `appKey` | 应用标识（旧文档里叫 AppId） | 不是手机号，是一串字符串 |
| `appSecret` | 应用密钥 | **等同密码**，只进 secret.json |
| `operatorId` | 一个**有权访问目标文档**的钉钉 userId | 必须是对该文档有读权限的人，否则接口报无权限 |
| `docUrl` | 钉钉项目计划文档的分享链接 | 见下文第 4 项 |

**怎么给我：** 你不用把密钥发我。你自己把 `secret.json` 建好填好，放在本机就行——
程序会去读它。我这边只需要你告诉我「填好了」，剩下的我写代码去读。

**安全约定（与 Teambition 凭据同规格）：**

- `data/dingtalk/secret.json` 已写进 `.gitignore`，**绝不入库**；
- 我不会用 `git add .`，只会显式 add 具体文件；
- 若你更希望用环境变量，也支持（优先级高于文件）：
  `DINGTALK_APP_KEY` / `DINGTALK_APP_SECRET` / `DINGTALK_OPERATOR_ID` / `DINGTALK_DOC_URL`。

> ⚠️ 顺手提醒一件既有的事：`data/iteration/state.json` **已被 git 跟踪**且含真实工时数据，
> 每次提交前都要确认它没被带上。

### 2. 权限点开通 —— 需要你去后台抄名字给我

**这一项我不要你「看着像就选」，要你把后台实际显示的名字抄给我。**
理由：钉钉开放平台的权限点名称与接口路径不是一一对应的，我只能给出**接口能力描述**，
后台到底叫什么名字，得以后台为准。上次 Teambition 就是吃了「凭猜名字去申请」的亏，绕了一圈。

请在 **应用 → 权限管理** 里按下面这几类去搜，把搜到的**权限点全名**抄给我（截图也行）：

| 用途 | 我依赖的接口 | 检索关键词建议 |
|---|---|---|
| 解析文档链接 → 拿到文档节点 | `/v2.0/wiki/*` | 知识库、文档节点、wiki |
| 读取表格/文档内容 | `/v1.0/doc/workbooks/*` | 文档、表格、workbook、内容读取 |
| 读取通讯录基础信息 | 通讯录相关 | 通讯录、用户信息 |
| （仅 2c 才需要）写表格 | 同上写入侧 | 表格编辑、内容写入 |

最后一行**现在不用申请**，等 2b 稳定后再说。

### 3. operatorId 到底怎么拿

两种方式，任选其一：

- **省事版**：你自己在钉钉里找到自己的 userId（管理员后台「成员管理」可见），直接填进 `secret.json`；
- **规范版**：给我通讯录读取权限，程序通过你的手机号/工号反查。

我建议用**省事版**——少申请一个权限点，少一个出错环节。

### 4. 目标文档链接 —— 并且要说明它是哪种文档

请提供：

1. 钉钉项目计划文档的**完整分享链接**（形如 `https://alidocs.dingtalk.com/...`）；
2. **它是「表格」还是「文字文档」** —— 这两类的接口完全不同，不能混用；
3. 该文档是否在**知识库**下（在的话走 wiki 节点接口，不在的话走文档接口）。

填进 `secret.json` 的 `docUrl`，或直接贴在聊天里都行（链接不是密钥，不算敏感）。

### 5. 网络连通性 —— 需要你在服务器上验一下

请确认跑本平台的那台机器**能访问 `api.dingtalk.com`**（443 出网）。

- 如果是内网，可能要配网关、代理或加白名单；
- 你们之前在 Teambition 上遇到过同类问题，所以这次先验，别等写完代码才发现连不上。

**验收方式：** 在服务器上执行
`curl -sS -o /dev/null -w "%{http_code}\n" https://api.dingtalk.com/v1.0/gateway/connections/open`
能返回 HTTP 状态码（哪怕是 4xx）就说明**通**了；卡住或报「无法解析主机」就是不通。

### 6. 是否有「文档变更」事件订阅 —— 需要你去后台看一眼

这个决定同步是「实时」还是「轮询」。请到 **事件订阅** 页面看有没有**文档/表格内容变更**类事件：

- **有** → 收到通知后自动拉取，能做到准实时；
- **没有** → 只能手动点「同步」按钮，或每天定时拉一次（我不建议高频轮询，浪费配额且无意义）。

我不预设答案，你看到什么告诉我什么。

## 四、需要你拍板的三个决策

| # | 决策 | 选项 | 我的建议 |
|---|---|---|---|
| 9 | **同步方向** | 只读拉取 / 双向 | **第一版只读**（钉钉为源，平台不回写）。先让链路稳定，双向留到 2c |
| 10 | **行匹配方式** | A：在钉钉表格保留 `_id`/`_parentId` 两列<br>B：用「名称指纹」匹配<br>C：平台把 `_id` 写回钉钉 | **A**。B 的风险是**一旦改名就丢字段**；C 需要写入权限，且改动钉钉表结构，牵扯更大 |
| 11 | **冲突以谁为准** | 钉钉优先 / 平台优先 / 逐条人工确认 | **逐条人工确认**。全局「谁优先」在真实使用中几乎一定会误删数据，等你用出感觉了再考虑自动化规则 |

第 10 项如果选 A，意味着**你的钉钉表格里会多两列 `_id` / `_parentId`**——
这两列对人不友好，但它是「改名不丢关联」的唯一可靠办法。**这一条要你明确点头**，因为它在改你的钉钉表。
