## 0. 一句话背景

平台要从「十几人的个人工具」变成「部门几百人 + 潜在全公司可用」。身份这件事必须一次性设计对，否则后面每加一个功能都要回来改。

**已有基础（不要重复实现）：**

| 已有 | 位置 | 说明 |
|---|---|---|
| 登录开关 | `server.js:48` `AUTH_REQUIRED` | 默认关。开`1`启用账号+密码+会话Cookie |
| 会话 | `db.js` `sessions` 表 | 30 天，HttpOnly Cookie `wb_session` |
| 密码哈希 | `db.js:159` `hashPassword` | scrypt 加盐 + `timingSafeEqual` |
| 角色权限 | `db.js:86` `DEFAULT_PERMISSIONS` | admin / pm / dev / viewer 四档 |
| **钉钉字段** | `db.js:35` `users.dingtalk_id` | ⭐ **已预留，本轮零 schema 改动** |
| 空密码用户 | `db.js:36` `password_hash` 可 NULL | ⭐ **纯钉钉登录用户已支持** |
| 登录页 | `login.html` | 已实现，本轮只需加内容 |
| 账号CLI | `user-cli.js` | 应急重置密码用 |

**结论：P0 几乎不用动地基，只在现有 `AUTH_REQUIRED` 之上加两个功能（批量建号 + 默认密码规则）。**

## 1. 已拍板的决策（不要再改）

| # | 决策项 | **最终结论** | 理由 |
|---|---|---|---|
| D1 | 身份主键 | **工号**（如 `10017xxx`）当 `users.id`<br>钉钉 userId 存 `dingtalk_id`<br>姓名仅用于显示 | 工号稳定、唯一、离职可回收；姓名会重名会改 |
| D2 | 默认密码 | **姓名缩写 + 固定后缀**（后缀自定，如 `2026`） | 用户明确要求，不按入职时间做复杂规则 |
| D3 | 强制改密 | **不强制**。仅在页面顶部给**可关闭**提示 | 用户明确要求，认为钉钉员工身份已足够 |
| D4 | 密码规则存放 | **配置文件，不写死在代码** | 代码进 git，写死等于公开 |
| D5 | 平台访问地址 | **第一阶段用纯内网 IP**（`http://10.13.39.160:8770`） | 照 CICD 先例；域名需走 IT 申请，不阻塞 |
| D6 | 第一阶段范围 | **只做 P0（工号+密码）**，钉钉接口不阻塞上线 | 七项核心能力里只有三项需要钉钉 |
| D7 | 钉钉接入顺序 | 先 P1 通讯录 → 再 P2 扫码/免登 | 通讯录权限是所有钉钉能力的基础 |
| D8 | 部门→角色 | 自动建号**一律 `viewer`**；角色只在平台里改，**不被钉钉覆盖** | 几百人规模，错给写权限要靠审计才能发现 |
| D9 | 离职处理 | 定时对账，钉钉查不到 → 平台自动停用 | 几百人系统最大的安全收益 |
| **D10** | **登录通道** | **密码登录与钉钉免登并存**。密码是**默认且长期保留**的通道，免登是叠加的增强 | 用户明确要求，理由见 §4。CICD 同样是双通道 |
| **D11** | **团队映射** | 平台 `config.js` 的 `TEAMS[].key` ↔ 钉钉部门名 **一一对应**（用户已确认） | 有对照表就不用维护映射表；也对得上「人力偏差按团队核算」的口径 |

### ⚠️ 一条必须写下来的长期风险

D3（不强制改密）意味着「姓名缩写+固定后缀」会成为**全公司长期存在的弱密码规则**。

**当前可接受**（纯内网 + 都是钉钉在职员工）。
**但：一旦平台暴露到公网（申请了外网域名、或通过快捷应用在内网外可访问），此决定必须重新评估。**

## 2. P0 · 工号 + 默认密码（**无依赖，立即可做**）

**目标**：几百人拿到工号就能登录，不需要钉钉、不需要域名、不需要任何审批。

### 2.1 需求

| # | 需求 | 说明 |
|---|---|---|
| P0-1 | 支持工号当账号 | `users.id` 已支持任意字符串，**验证即可，无需改代码** |
| P0-2 | 批量建号 | 从名单一次性建几百个账号，全部 viewer + 默认密码 |
| P0-3 | 默认密码生成规则 | 姓名缩写 + 固定后缀，规则从配置读 |
| P0-4 | 首次登录提示 | 顶部可关闭横幅：「你在使用初始密码，建议修改」 |
| P0-5 | 保留 admin 手动维护 | 现有 `/api/auth/users*` 接口与 `user-cli.js` 不动 |

### 2.2 实现要点

**① 新增配置文件** `data/auth-config.json`（**加入 `.gitignore`**）

```json
{
  "_说明": "登录相关配置。改这里重启生效，不要写进代码。",
  "defaultPasswordSuffix": "2026",
  "defaultPasswordMode": "initials+suffix+last4",
  "forceChangeOnFirstLogin": false
}
```

> `defaultPasswordMode` 预留多态，已实现两种：`initials+suffix+last4`（当前）和
> `initials+suffix`（老规则，兼容已发出去的老密码）。**2026-09-24 落实**：
> 公式为「姓名缩写（首字母大写）+ 年份 + 工号后4位」，例 `Cdp20267968`。
> 读不到文件时使用**内置默认值**并打印一条提示，不能因为文件缺失就崩。

**② 姓名缩写算法**

- 中文名「张三」→ `zs`；英文名 `chendanping` → `cdp`（取每个字/音节首字母）
- 中文名的拼音转换**不引入依赖**。做法：让批量建号的名单里**带一列"密码前缀"**，
  由人工/Excel 公式生成好；程序把它规范成首字母大写后拼进密码。
- 这一列**必填**：它是密码的第一段，缺了就没法开户。
- **重名不需要额外处理**：两个张磊缩写都是 `zl`，但工号后 4 位不同
  （`Zl20263853` / `Zl20263228`），拼出来天然不一样。
- **这样避免引入拼音库（零依赖是本项目的硬约束）**，也避免多音字出错。

**③ 批量建号脚本** `user-import.js`（新文件，与 `user-cli.js` 并列）

```
用法：
  node user-import.js --dry-run docs/samples/员工名单.csv
  node user-import.js docs/samples/员工名单.csv

CSV 列（首行表头，UTF-8）：
  工号,姓名,密码前缀[,角色]
  10017xxx,张三,zs
  10018xxx,李四,ls,pm        ← 角色列可选，缺省 viewer
```

行为：

- `--dry-run` 只打印将要创建/跳过的账号，**不写库**
- 已存在的工号**跳过，不覆盖其密码与角色**（重要！否则重跑会把别人改过的密码冲掉）
- 结束时打印汇总：新建 N 个 / 跳过 M 个 / 失败 K 个（附原因）
- 每建一个号写一条 `audit_log`（`module='auth'`, `action='批量建号'`）
- **先停服务再执行**（与 `user-cli.js` 同一约定，避免 SQLite 写竞争）

**④ 首次登录提示**

- 判断条件：当前用户的 `password_hash` 与「初始密码哈希」一致 → 说明没改过
- **实现方式**：建号时在 `users` 表加一列 `pwd_is_initial INTEGER DEFAULT 0`（**这是本轮唯一的 schema 改动**）
- 登录接口返回 `isInitialPwd: true`，前端顶部渲染一条可关闭横幅
- 用户改密后置 `0`

> 备选（若不想改表）：把初始密码哈希存进 `meta` 表做比对。**不推荐** —— 改一次密码就要重算，且无法区分"改过又改回去"。**建议加列**，一次性的小改动。

### 2.3 验收标准

- [ ] `node user-import.js --dry-run 名单.csv` 输出正确，数据库无变化
- [ ] 正式导入 200+ 行，全部成功，`user-cli.js list` 可见
- [ ] 用工号 + 默认密码能登录，进去是 viewer 权限（**验证：改不了数据，返回 403**）
- [ ] 顶部出现初始密码提示，改密后提示消失
- [ ] 重复导入同一份名单，**不覆盖已改过的密码**
- [ ] `npm test` 全绿

## 3. P1 · 通讯录同步（**v1.2 恢复为正式范围**）

> **定位（2026-09-22 决策变更）：从「可选」改为「正式范围」。**
> 原因：用户明确要求「打通整个公司钉钉」，而不是只打通文档库。
> 通讯录是**所有钉钉能力的基础**——免登要知道「这个人是谁」，
> 组织树要知道「这个人在哪个团队」，离职对账要知道「这个人还在不在」。
>
> **v1.1 曾把它降级为可选**，理由是「手工同步每季度 5 分钟」。
> 这个理由在**「只要几百人能登录」**的目标下成立；
> 但在**「平台与钉钉双向打通」**的目标下不成立——手工同步出不来免登，也出不来组织树。

**前置条件**：appKey/appSecret（已有）+ 通讯录权限点（**实测已开通**，见 §5.3）。

### 3.1 要做什么

| # | 需求 | 状态 |
|---|---|---|
| P1-1 | 钉钉 API 客户端：换 access_token（含缓存与过期重取） | ✅ 已有（`dingtalk-ping.js` 已验证） |
| P1-2 | 拉部门列表 → 拉各部门成员 | ⚠️ 路径待定（见 §5.3 待办） |
| P1-3 | 与 `users` 表对账：**只新增，不改已有账号的角色和密码** | 待做 |
| P1-4 | 写一条对账报告（新增/停用/跳过各多少），供人工复核 | 待做 |
| **P1-5** | **团队映射**：平台 `TEAMS[].key` ↔ 钉钉部门名 | 待做（规则见 §3.5） |

### 3.2 硬约束

- **自动建号角色一律 `viewer`**（D8）
- **改角色永不自动**：钉钉里转岗了，平台只提示「建议复核」，不自动改权限
- **停用可自动，但要有日志**：`audit_log` 记录「因钉钉对账停用」，便于回溯
- access_token 缓存**存内存 + 落 `data/dingtalk/token.json`**（已 gitignore），**不要每次请求都换**（钉钉有限流）

### 3.3 待实测验证的未知项（**不预设结论**）

| 未知 | 影响 | 兜底 |
|---|---|---|
| 通讯录接口在 `api.dingtalk.com` 的**正确版本写法** | 决定 P1 能不能开工 | 试 `Version` 请求头；或改走 `oapi.dingtalk.com` 旧版接口 |
| 接口能否返回**工号**字段 | 决定 `users.id` 用什么 | 退回用手机号；或退回 P0 的 CSV 导入 |
| 接口限流阈值 | 决定批量拉取要不要分批 | 分批 + 退避重试 |

> **Teambition 的教训：不实测不设计。** 拿到凭据后**第一件事是写一个最小连通脚本**（换 token → 拉 1 个部门 → 打印），跑通再写正式逻辑。这一步没跑通之前，P1 的同步逻辑一行都不写。

### 3.5 团队映射规则（**D11：用户已确认一一对应**）

平台 `config.js` 里的 `TEAMS` 有 18 个团队，形如 `APP开发-阳光云`、`测试部-应用软件测试-云服务`。
用户确认：**这些团队与钉钉部门一一对应**，因此**不需要维护对照表**。

```
钉钉部门名  ──(完全相同)──▶  TEAMS[].key
```

**落地时的三个检查点**（这三点不做，映射会静默错位——错位了不报错，只是人力偏差算歪）：

1. **大小写与空格**：`TEAMS[].key` 的比较已经是大小写不敏感的（`config.js:3` 注释），
   但钉钉部门名可能带全角空格/不可见字符，比对前要 `trim()` + 全角转半角。
2. **反向映射**：`TEAMS[].dept`（如 `APP开发`）是**上级部门**，`key` 才是**具体部门**。
   钉钉是树，平台是平表 —— 拉取时要按**叶子部门**对，不要按父部门对。
3. **对不上的怎么办**：对不上的部门**不报错、不静默忽略**，写进 P1-4 的对账报告里，
   标成「钉钉有、平台无」和「平台有、钉钉无」两类，人工过一眼。
   这与 `IGNORED_TEAM_PATTERNS`（`config.js:30`）是两回事：那里是**故意忽略**，这里是**发现了新情况**。

### 3.4 不做 P1 的代价（明确承担）

**「离职了账号还在」要靠手工处理。** 几百人的系统里这是最常见的漏洞。
**修复方式**：每季度导一次钉钉通讯录，与 `user-cli.js list` 对一遍，手工停用。

## 4. 钉钉免登（**v1.2：要做，但与密码登录并存**）

> **定位（2026-09-22 决策变更）：要做。但它是【叠加】的，不是【替代】的。**
>
> v1.1 曾判定「建议不做」，理由是「只省一个月敲 11 个字符」。
> 这个理由**在当前证据下不成立**：用户明确了「打通整个公司钉钉」的目标，
> 而免登是「员工点一下就进来」这个体验的唯一实现方式。
>
> **但 v1.1 那条担心的失败风险仍然成立**（纯内网 IP 大概率过不了回调域名白名单）。
> 所以顺序不变：**免登排在最后，且不通也不影响任何已交付能力。**

### 4.0 ⭐ 双通道原则（**D10，最重要的一条**）

```
┌─────────────────────────────────────────────────────┐
│  登录页                                              │
│                                                      │
│  ┌───────────────────────────┐  ← 默认展示、长期保留  │
│  │  工号 + 密码              │                      │
│  └───────────────────────────┘                      │
│                                                      │
│  ┌───────────────────────────┐  ← 免登通了才出现      │
│  │  钉钉扫码 / 一键登录       │                      │
│  └───────────────────────────┘                      │
└─────────────────────────────────────────────────────┘
```

**为什么是并存，不是替代**——四条理由，每条都真实会发生：

| # | 场景 | 只有免登会怎样 |
|---|---|---|
| 1 | **外部人员**（供应商、外包、实习未入职）没有钉钉账号 | **完全进不来** |
| 2 | **钉钉侧故障 / 限流 / 维护** | 全公司都进不来，平台陪着一起挂 |
| 3 | **联调期**：免登没配好之前 | 没人能用，开发无法验证任何功能 |
| 4 | **内网到不了钉钉**（断网、代理变更、白名单变了） | 同上 |

**参照**：用户提到的 CICD 平台就是双通道。这不是妥协，是标准做法。

**实现要点**：
- **登录页默认聚焦密码框**，不是扫码按钮 —— 大多数人的日常路径是密码登录
- 免登入口**只在配置完整时才渲染**（appKey/appSecret/回调地址三项齐全），否则整个按钮不出现，
  而不是出现一个点了报错的按钮
- **两条通道最终产出同一个东西**：`db.createSession(userId)` → 同一个 `wb_session` Cookie。
  下游（权限门禁、审计、`Platform.currentUser()`）**完全不需要知道用户是从哪条路进来的**
  ⭐ **这是关键设计**：免登不应该污染权限模型
- 审计日志区分来源：`action: '登录'`，`details` 里记 `通道=密码` 或 `通道=钉钉免登`

### 4.1 两条路，成本不同

| | 钉钉扫码登录 | 钉钉免登 |
|---|---|---|
| 场景 | 浏览器打开平台，扫一下 | 在钉钉客户端里点开应用 |
| 钉钉服务器需访问你的平台吗 | ❌ **不需要**（浏览器主动连钉钉） | ✅ **需要**（钉钉要跳回你的地址） |
| 纯内网能跑通吗 | **大概率能**（待实测） | **大概率不能** |
| 额外要求 | 回调域名白名单 | 公网可达 + 回调域名白名单 |

**若将来要做：优先做扫码，免登等有公网域名再说。**

### 4.2 实现时的两个必做项（**参考内部「评优材料评审系统」的成功实现**）

内部那个平台的 `/sso/callback` 已经跑通了同一套流程，值得照抄它的两个做法：

**① `state` 防重放**（我们**现在没有**，必须补）

```
登录前：生成随机 state → 存 sessionStorage → 拼进钉钉授权链接
回跳后：比对回传的 state 与 sessionStorage 里的 → 不一致一律拒绝
```
没有这一步，攻击者可以伪造回跳请求把用户登进错误的账号。

**② 回跳路径 `targetPath`**（把用户送回他原本要去的地方）

```
登录前记录 targetPath → 存在 sessionStorage → 登录成功后 replace(targetPath)
```
我们的 `login.html` 已有类似的 `next` 参数，但存储位置和校验规则要与之统一，
否则会出现「钉钉登完跳回首页，而不是我本来要开的那个项目」。

**③ `FORBIDDEN` → 专门的「无权限」页面**（**我们现在完全没有这个状态**）

内部平台在换身份返回 `FORBIDDEN` 时跳 `/no-access`。
对应到我们这边，通讯录同步一上线就会撞上这个场景：
**「这个人在钉钉里存在，但平台里还没给他角色」**。
没有这个页面，他看到的会是空白或报错。**这个页面必须有**，且文案要说清
「已成功登录，但尚未分配权限，请联系管理员」。

### 4.3 什么情况下才值得回来做

- 用户明确抱怨"每天登录太烦"（**先确认这是真抱怨，不是想象**）
- 或平台要做移动端场景（在钉钉里点开即用，不输任何东西）

**若实测不通过**：放弃免登，工号+密码方案已覆盖 100% 的人，**这不是缺陷**，
因为 D10 保证了密码通道永远在。

---

## 4.5 P1.5 · 钉钉工作通知（**可选，但优先级高于 P1/P2**）

> **定位：如果开发者权限批下来、且只想在钉钉上花一份力气，花在这个上。**

**为什么它比 P1/P2 更值得做**：P1/P2 解决的都是"**人去找平台**"，
而工作通知解决的是"**平台主动找人**"—— 这才是打通的真正价值。

| 能力 | 体验 |
|---|---|
| 风险预警推到钉钉 | 不用打开平台也知道哪里不对 |
| 周报推送到钉钉 | 一键发到群 |
| 待办催办 @ 人 | 直接戳到人 |

**成本**：一个权限点（工作通知/机器人相关），比 P1/P2 都低。
**与 AI 主线的结合点**：`plan-ai-master.md` §4.4 列的「群机器人 / 待办审批」就是它。

## 5. 需要公司侧配合的事

> **状态：卡点已解决（2026-09-21）。** 详见 5.2。本节保留 5.1 的成因记录，
> 是为了后人再遇到「为什么我建不了应用」时不用重新查一遍。

### 5.1 起因：没有钉钉「企业内部应用」的创建权限

**已核实**：能建「快捷应用」，**建不了「企业内部应用」**。

| | 企业内部应用 | 快捷应用（现在有的） |
|---|---|---|
| 有 appKey/appSecret | ✅ | ❌ |
| 能申请权限点 | ✅ | ❌ |
| 能调 OpenAPI | ✅ | ❌ |
| 本质 | 独立应用 | **只是个链接卡片** |

**本质原因**：账号缺「开发者权限」。这是组织权限问题，不是技术问题。

### 5.2 ✅ 已解决：IT 代建应用 + 把本人加为应用开发者

**现状（2026-09-21 确认）**：公司 IT **无法直接分配开发者权限**，但可以**代为申请并创建应用**，
**创建后把申请人的工号加为该应用的「应用开发者」**。

**这个安排完全满足现阶段所有需求，不需要再争取别的。**

| 能力 | 有了它够不够 |
|---|---|
| 拿到 appKey / appSecret | ✅ 够 |
| 自行申请权限点 | ✅ 够（应用开发者身份可以操作） |
| 调 OpenAPI（通讯录、工作通知） | ✅ 够 |
| 做免登集成 | ✅ 够（用户原话验证） |

**⚠️ 唯一的注意点：权限点审批仍要走流程。**
「应用开发者」能**申请**权限点，但审批要有权的人点通过。
**所以：拿到应用 ≠ 马上能调接口，别在权限点批下来之前就假设能跑。**
（这正是「先 P0 上线、不依赖钉钉」这个决策的价值所在。）

**沟通话术（备用，若流程上还需要补说明）：**

> 我要做内部项目管理平台，需要和钉钉打通。我已提交集成申请，麻烦帮我创建企业内部应用，
> 并把我的工号加为该应用的**应用开发者**，这样我后续可以自行申请权限点、做免登集成。

### 5.3 需要申请的权限点（**2026-09-22 实测，非推测**）

> **本节已改为实测结果。** 原版是按关键词猜的，实测证明**猜的不对**：真正缺的只有 2 个，
> 而原清单里的通讯录三项**早就开通了**。以本节为准。

**实测方法**（可复现）：故意调用目标接口，钉钉缺权限时回 **403** 并在
`accessdenieddetail.requiredScopes` 里**写明它要的真实权限点名**。这比任何文档都准——
钉钉后台的权限点名称与接口路径不是一一对应的。
**判据：403 + `requiredScopes` = 真缺权限；404 `InvalidAction.NotFound` = 路径写错；
其余业务错误码（`invalidParameter.*` / `InvalidVersion` / `MissingrobotCode`）= 权限已通。**

**❌ 真缺（就这 2 个，一次提交）**

| 权限点名（照抄） | 用于 | 实测证据 |
|---|---|---|
| `Wiki.Node.Read` | 解析文档链接、列知识库节点 | `POST /v2.0/wiki/nodes/queryByUrl` → 403 |
| `Document.Workbook.Read` | 读表格 sheet 与单元格 | `GET /v1.0/doc/workbooks/.../sheets` → 403 |

**✅ 已开通，不要再申请（实测已通）**

| 能力 | 实测返回 | 说明 |
|---|---|---|
| 查用户 / 按 userId 查人 | `invalidParameter.user.notFound` | 请求已进业务层，权限没问题 |
| 部门列表 / 子部门列表 | `InvalidVersion` | 路径对，只是版本参数写法待调（见下） |
| 机器人单聊 / 群聊 | `MissingrobotCode` / `MissingmsgParam` | 只差 `robotCode` 配置，非权限 |

**⚠️ 原清单的纠错对照**

| 原清单说的 | 实测结论 |
|---|---|
| `Wiki.Node.Read` | ✅ 对，确实缺 |
| `Wiki.Workspace.Read` | ❌ 探测中从未被要求，**不用申请** |
| `Contact.User.Read` | ❌ **已开通** |
| `Contact.Department.Read` | ❌ **已开通** |
| `qyapi_get_member` | ❌ **已开通**；且该名字属旧版 qyapi（`oapi.dingtalk.com`），
本平台走的是新版 OpenAPI（`api.dingtalk.com`），不必管 |
| —（原清单漏了） | ➕ **`Document.Workbook.Read`** |

> **⚠️ 铁律：把后台显示的权限点全名原样抄回（截图最好），不要挑、不要猜。** Teambition 的教训。

**待办（不阻塞，路径已探明但版本参数未定）**：通讯录接口在 `api.dingtalk.com` 的
正确版本写法尚未试出（`/v2.0/contact/departments` 回 `InvalidVersion`）。
下一步是试 `Version` 请求头，或改走旧版 `oapi.dingtalk.com`。
**权限本身已开通，这是纯技术细节，不影响申请。**

### 5.4 域名（**免登才需要，P1 通讯录不用**）

| 系统 | 地址 | 规律 |
|---|---|---|
| OA | `https://bpm.sungrow.cn/#` | `<系统名>.sungrow.cn` |
| 缺陷DTS | `http://smartdts.sungrow.cn:8090/login` | 同上 |

**规律确认**：不是"有一个统一平台域名"，而是**每上一个内部系统配一个子域名**。

**将来真要做 P2 时的申请话术（比问"有没有域名"高效十倍）：**

> 「OA 是 bpm.sungrow.cn，缺陷系统是 smartdts.sungrow.cn，我这个项目管理平台也想申请一个，比如 pm.sungrow.cn，指向 10.13.39.160:8770。要走什么流程？」

**P0 / P1 / P1.5 都不需要域名**，纯内网 IP 即可。

### 5.5 现在就能用的：快捷应用当入口（零申请）

**已建好的快捷应用别浪费** —— 它可以把平台挂进钉钉工作台：

```
同事打开钉钉 → 工作台 → 点「项目管理平台」卡片
   → 钉钉内置浏览器打开 http://10.13.39.160:8770
   → 落在内网，能打开（连公司WiFi/VPN 时）
   → 工号 + 默认密码登录
```

**今天就能配，零审批零代码。** 唯一限制：需连内网（WiFi 或 VPN）。

## 6. 网络连通性

**本机已实测通过**（`node check-network.js`，2026-09-20）：

```
api.dingtalk.com     DNS ✔ 106.11.35.100   HTTPS ✔ HTTP 404  159ms
oapi.dingtalk.com    DNS ✔ 106.11.40.32    HTTPS ✔ HTTP 200  155ms
login.dingtalk.com   DNS ✔ 106.11.40.32    HTTPS ✔ HTTP 302  140ms
结论：3/3 通
```

**两条注意：**

1. **部署到服务器后必须重跑 `check-network.js`** —— 开发机通了不代表服务器通。
2. ⚠️ **本机系统环境变量里设着 `NODE_TLS_REJECT_UNAUTHORIZED=0`**，等于**关闭了 HTTPS 证书校验**。
   - 现在不阻塞开发，但**上线前必须处理**：正确做法是装公司根证书并**恢复校验**。
   - `appSecret` 要经这条链路传给钉钉，一直关着校验等于裸奔。
