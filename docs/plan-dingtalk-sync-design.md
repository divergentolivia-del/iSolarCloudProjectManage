# 项目计划 ↔ 钉钉文档 打通设计方案

> 目标：钉钉上的项目计划表格更新后，平台上对应的项目计划内容也同步更新；
> 两边表格格式不必完全一致，靠字段映射对上即可。
>
> 设计参考：本方案沿用「项目 ↔ Teambition 关联」（PR #10）的思路 ——
> 应用凭据换 token、只读单向拉取、每子项 soft-catch、把外部 ID 存在本方记录上。

---

## 一、总体策略：分三步走，每步都能单独交付

| 步骤 | 内容 | 依赖 | 价值 |
|---|---|---|---|
| **2a** | 手工上传钉钉导出的 Excel → 解析 → 预览 → 填充表单 | **无外部依赖** | 立刻可用，且是 2b 的解析内核 |
| **2b** | 关联钉钉文档链接 → 一键拉取最新内容 → 预览差异 → 应用 | 钉钉应用凭据 + 权限 | 不用每次手工导出 |
| **2c** | 定时/事件触发自动同步 | 需确认钉钉是否提供文档变更事件 | 真正的「自动同步」 |

**关键点：2a 的解析器与映射层，就是 2b/2c 的内核。** 上传 Excel 和从接口拉取，
差别只是「数据从哪来」，往后的映射、匹配、预览、写入完全共用一条链路。
所以先做 2a 不是权宜之计，而是正确的分层。

## 二、接口调研结果（已核实路径，未实际调用）

来源：钉钉官方开放平台产品线的开源 CLI [ianen/dingtalk-cli](https://github.com/ianen/dingtalk-cli)
（同类工具还有 Dify 的 DingTalk Spreadsheet 插件、Quick BI 的钉钉表格数据源，
可交叉印证「钉钉表格确实提供读取接口」）。

> ⚠️ **诚实声明**：以下路径来自开源实现，**我没有实际调用验证过**。
> 上一次我照官方示例脚本写 TB 迭代接口路径，结果实测不存在（`sprints` 实为 `sprint/search`），
> 所以这份清单在拿到凭据实测前，只能当作「调研结论」而非「已验证事实」。

### 认证

```
POST https://api.dingtalk.com/v1.0/oauth2/accessToken
     body: { appKey, appSecret }  →  { accessToken, expireIn }

后续请求头：x-acs-dingtalk-access-token: <accessToken>
多数文档类接口还要求 query 参数：operatorId=<钉钉 userId>
```

与 TB 的模式几乎一致（appId/appSecret 换 token + 操作人身份），
所以 `modules/tb/client.js` 里的 **token 缓存 + 并发去重** 可以直接照搬。

### 定位文档

```
POST /v2.0/wiki/nodes/queryByUrl      粘贴钉钉文档链接 → 解析出 nodeId
GET  /v2.0/wiki/workspaces            知识库列表
GET  /v2.0/wiki/nodes                 节点（文档）列表
GET  /v2.0/wiki/nodes/{nodeId}        节点详情
```

`queryByUrl` 很关键：**你只需要粘贴文档链接**，不用去后台翻 ID。

### 读取表格内容

```
GET /v1.0/doc/workbooks/{workbookId}/sheets?operatorId=...
        列出工作表（钉钉表格文件后缀是 .axls）

GET /v1.0/doc/workbooks/{workbookId}/sheets/{sheetId}/ranges/{A1:Z80}
        ?operatorId=...&select=displayValues
        读取指定区间的「显示值」
```

**两个已知约束：**

1. **按区间读，不是整表读。** 开源实现默认 `A1:Z80`，超出要自己翻页
   （按行分段多次请求再拼接）。大表必须实现分段拉取与拼接。
2. **取 `displayValues`（显示值）而不是原始值。** 好处是日期、百分比拿到的是
   人看到的字符串；代价是**日期格式依赖钉钉的显示设置**，解析时必须容错
   （`2026/9/1`、`2026-09-01`、`9月1日` 都要能认）。

## 三、数据模型改动

在计划对象上增加钉钉关联字段（与 TB 关联在项目对象上加 `tbProjectId` 同构）：

```js
{
  dtNodeId:     '',   // 钉钉文档/表格 nodeId（= workbookId）
  dtSheetId:    '',   // 具体工作表 id
  dtDocUrl:     '',   // 原始链接，便于回跳
  dtDocTitle:   '',
  dtLinkedAt:   '',   // 关联时间
  dtLastSyncAt: '',   // 最近同步时间
  dtFieldMap:   {},   // 列映射（见下节），随计划持久化
  dtRowKeys:    {}    // 行指纹 → 本方 id，用于增量匹配（见第五节）
}
```

后端校验参照 `modules/project/routes.js` 里对 `tbProjectId` 做 24 位十六进制校验的做法，
对 `dtNodeId` 做格式与长度校验，避免脏数据落库。

## 四、字段映射层（解决「格式不一模一样」）

不做硬编码列名。三段式：

**1. 自动猜**
用同义词字典 + 归一化（去空格/全半角/括号）做表头匹配：

```
任务名称 ← 任务名 / 名称 / 工作内容 / 事项 / Task / 任务
负责人   ← 责任人 / owner / 执行人 / 主责人 / 负责人员
开始     ← 开始时间 / 计划开始 / 起始日期 / start
结束     ← 结束时间 / 计划结束 / 截止日期 / 完成时间 / end
状态     ← 当前状态 / 进展 / status
进度     ← 完成度 / 完成率 / progress / 进度%
```

**2. 人工确认**
猜完在界面上以「我们的字段 ← 下拉选钉钉列」的形式展示，你可改。
未匹配上的字段留空即「不导入」。

**3. 记住**
映射存进 `dtFieldMap` 随计划持久化，下次同步直接复用，不用重配。
**钉钉表格加列/改列名时，只需改映射，不用改代码** —— 这是不硬编码的全部理由。

层级识别沿用 WBS 导入已有那套：父子列 / `1.1` 编号 / 缩进；
识别不出就全部作为一级，再用**拖拽功能**手工调整（拖拽刚做好，正好接上）。

## 五、增量同步最大的技术风险：怎么认出「这行还是上次那行」

这是整个方案最难的一点，**必须先定方案，否则同步会把数据搅乱**。

钉钉表格的行没有稳定 ID。三条路：

### 方案 A：让钉钉表格带上我们的 `_id`（**推荐**）

我们导出的 Excel 已经在每张表末尾输出 `_id` / `_parentId`（阶段一已实现）。
若钉钉表格是**由我们导出的文件上传上去的**，`_id` 列天然存在 → 匹配 100% 准确。

- 优点：完全可靠，改名、挪位置、调层级都能正确跟踪
- 代价：需要你**保留那两列**（可以隐藏，别删）

### 方案 B：行指纹模糊匹配（无 `_id` 时的兜底）

指纹 = 归一化(层级编码 + 名称)。存进 `dtRowKeys` 做映射表。

- 缺点很明确：**改名 = 认不出 → 会被当成「删旧增新」**，
  该行在平台侧填的其他字段（负责人、进度）会丢
- 因此这条路必须配合「差异预览 + 人工确认」，不能自动应用

### 方案 C：回写 `_id` 到钉钉表格

首次同步后把我们的 `_id` 写回钉钉表格一列，之后走方案 A。
需要**写权限**，且改动了你的钉钉文档 —— 需你同意。

**建议：默认走 A，检测不到 `_id` 列时自动降级到 B 并明确提示风险。**

## 六、同步流程与冲突处理

```
拉取钉钉表格
  → 按 dtFieldMap 映射成平台数据结构
  → 与平台现有数据做 diff（按第五节的匹配键）
  → 生成变更清单：新增 N / 修改 M / 删除 K
  → 【预览页】列出每一条，标出改了哪个字段（旧值 → 新值）
  → 你确认后才写入
```

**三条硬性原则：**

1. **绝不静默覆盖。** 你可能在平台侧也改过同一行，直接覆盖等于丢工作。
2. **对「平台侧也被改过」的行单独标记**，让你逐条选择以哪边为准。
3. **删除只提示不自动执行。** 钉钉那边删一行，可能只是重构表格，
   不代表任务取消。默认保留并标记「钉钉侧已不存在」。

第一版**只做单向只读拉取（钉钉为源，平台不回写）**，
和 Claude Code 做 TB 关联时选的「方案 B 只读拉取」同一思路：风险最低，先跑通链路。

## 七、2c 自动同步：仍有一个未知

「钉钉文档更新了平台自动更新」的理想形态需要**文档变更事件**。
钉钉是否对文档/表格提供变更回调（webhook / Stream 模式事件），**我尚未查证**。

- **若有**：订阅事件 → 收到通知 → 拉取 → 生成变更清单 → 站内提醒你确认
- **若没有**：只能轮询。建议**手动「同步」按钮 + 可选定时轮询（如每天一次）**，
  而不是高频轮询（既浪费配额，也没意义）

这一项我不承诺，等实测。

## 九、落地顺序建议

1. **先做 2a**（上传钉钉 Excel → 映射 → 预览 → 填充）—— 只等你的样例文件，其他都不依赖
2. 你并行去申请钉钉应用与权限
3. 凭据到手后做 2b，**第一步是写一个最小连通性验证**：
   换 token → `queryByUrl` 解析你的文档链接 → 读一个区间打印出来。
   跑通了再往上搭，**不先实测就设计同步逻辑等于空中楼阁**（TB 那次的教训）
4. 2b 稳定运行一段时间后再评估 2c 是否值得做
