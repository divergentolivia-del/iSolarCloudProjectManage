## 0. 一句话

**身份登录和钉钉打通是两条独立的线。** 登录解决「你是谁」，钉钉解决「你能用钉钉的哪些能力」。前者换一种登录方式，后者一行都不用改。

这个区分是本文存在的唯一理由 —— 之前把「钉钉免登」当成打通钉钉的必经之路，是错的。

---

## 1. 两条线，互不依赖

```
┌──────────────────────────────┐   ┌──────────────────────────────┐
│  线 A：身份 / 登录            │   │  线 B：钉钉能力               │
│  解决「你是谁」               │   │  解决「能用钉钉做什么」        │
├──────────────────────────────┤   ├──────────────────────────────┤
│  A1 工号 + 密码   ✅ 已做      │   │  B1 知识库/文档同步  ⏳ 差权限 │
│  A2 公司 SSO      📋 待申请    │   │  B2 通讯录           ⏳ 待做   │
│  A3 钉钉免登      ⏸️ 排最后    │   │  B3 消息通知/机器人   ⏳ 待做   │
│                              │   │  B4 会议/日程        💤 可选   │
├──────────────────────────────┤   ├──────────────────────────────┤
│  产物：wb_session Cookie      │   │  凭据：appKey / appSecret     │
│  依赖：无外部系统             │   │  依赖：与谁登录无关            │
└──────────────────────────────┘   └──────────────────────────────┘
                    ↓                            ↓
              同一个 users 表（users.dingtalk_id 关联）
```

**核心事实**：**哪怕一行钉钉登录代码都不写，B1~B4 照样能全部打通。** 它们靠的是应用凭据，不是某个人的登录态。

## 2. 线 A：身份 / 登录

### A1 工号 + 密码（✅ 已完成）

平台默认通道，**长期保留**。批量建号见 `user-import.js`，密码规则 `姓名缩写 + 后缀`。

### A2 公司 SSO（📋 待申请）⭐ 优先做

**不是钉钉**，是公司统一登录 `https://sso.sungrow.cn/sso/login`。

**为什么它比钉钉免登好**：

| 维度 | 公司 SSO | 钉钉免登 |
|---|---|---|
| 外部系统要访问我们的内网地址吗 | ❌ **不需要**（浏览器自己跳） | ✅ 需要（过不了白名单） |
| 纯内网 IP 能跑通吗 | ✅ **能** | ❌ 大概率不能 |
| 返回什么 | **工号**（可直接当 `users.id`） | 钉钉 userId（还要再换） |
| 申请路径 | 走「流程数字化中心」 | 配权限点 + 回调白名单 |

**流程**（据 `钉钉开发/SSO申请.docx`）：

```
① 未登录 → 跳转
   https://sso.sungrow.cn/sso/login
     ?response_type=code          ← 定值
     &client_id=<SSO 提供>         ← 待申请
     &redirect_uri=<我们的回调地址>
     &state=<我们生成的随机串>      ← 防重放
② 用户在 SSO 登录 → 跳回
   <我们的地址>/sso/callback?code=ZEAVvM
③ 后端用 code + 密钥 换【工号】
④ 用工号匹配 users.id → 建会话（与密码登录同一个 wb_session）
```

**待申请清单**（去「流程数字化中心」）：

| # | 要什么 | 说明 |
|---|---|---|
| 1 | `client_id` | 拼在跳转链接里 |
| 2 | 密钥 `client_secret` | 换工号时用 |
| 3 | 换工号的接口地址与返回字段 | 文档没写，必须问 |
| 4 | 回调白名单是否接受**纯内网 IP + http + 端口** | 登记值：`http://10.63.139.103:9680/sso/callback`（端口 9680 已与服务器管理员确认，避开 9003）|
| 5 | 有无测试环境 | 文档提到「给一个测试、一个开发的材料」，说明有 |

**必做的两个细节**（照抄内部「评优材料评审系统」的成功实现，它的 `/sso/callback` 已跑通）：

- **`state` 防重放**：服务端生成随机串存内存表，10 分钟过期，**用掉即删**；回跳时比对，不在表里 / 已用过 / 已过期一律拒绝
- **`next` 回跳**：记录用户原本要去哪，登录后送回那里（与现有 `login.html` 的 `next` 参数统一）

> ⚠ 原计划把 state 存 sessionStorage 由前端比对 —— 已改为服务端内存表。
> 原因：state 只存浏览器，攻击者拿到回调链接就能反复重放；放服务端才能真正做到一次性。
> 实现见 `modules/sso/routes.js`。

### A3 钉钉免登（⏸️ 排最后）

**不删，但排最后。** 理由见 A2 对照表 —— SSO 能达成同样效果而风险小得多。

**什么情况下才回来做**：员工主要在钉钉客户端里使用平台（点开即用，不输任何东西），而 SSO 的体验不够。

**若最终不做，这不是缺陷** —— A1 + A2 已覆盖全部场景。

### ⭐ 三条通道的汇合点

```
A1 密码  ─┐
A2 SSO   ─┼─→ db.createSession(工号) ─→ wb_session Cookie
A3 免登  ─┘
```

**下游（权限门禁、审计、`Platform.currentUser()`）完全不需要知道用户从哪条路进来。**
这是关键设计：**新增登录方式不应该污染权限模型。**

审计日志区分来源：`action: '登录'`，`details` 记 `通道=密码` / `通道=公司SSO`。

### 「无权限」页面（三通道都需要）

**已有的场景会先撞上**：SSO 认得你是员工，但平台里还没给你建账号（工号对不上）。
必须明确提示「登录成功，但平台尚未分配权限，请联系管理员」，而不是白屏或报错。

### B1 知识库 / 文档同步（⏳ 正在做）

项目计划 ↔ 钉钉文档双向同步。**权限已就绪**；解析内核 + 预览确认页已完成，见 `plan-dingtalk-checklist.md`。
**已放下（不再继续追）**：`operatorId` 需要真正的 unionId，而现有接口拿不到 —— 详见下方说明。

> **为什么放下 rather than 继续查 userid→unionId 映射**
>
> 报错序列证明字段名没错：key 缺失时报 `MissingoperatorId`，值无效时报 `paramError-operatorId`。
> 也就是说，`operatorId` 是**字段名**，缺的是一个**合法的 unionId 值**。
>
> 但钉钉侧没有「用手机号 / 姓名 / 工号反查 unionId」的公开接口 —— 我扫了 15252 条通讯录档案，
> 既没有「陈丹萍」，也没有 `chendanping`，也没有匹配的 `job_number`。
>
> **继续投入不划算**：SSO 走通后返回的**工号**（如 10017968）直接匹配 `users.id`，
> 拿它就够了 —— unionId 这条线对平台要解决的问题（识别是谁）没有额外价值。

### B2 通讯录（⏳ 待做）

**两个用途**：

| 用途 | 说明 |
|---|---|
| **团队映射** | 钉钉部门 ↔ 平台 `config.js` 的 `TEAMS[].key`，**用户已确认一一对应**，零对照表 |
| **离职对账** | 钉钉查不到的人 → 平台自动停用账号。几百人系统最大的安全收益 |

**同时它也是「谁在操作」可追溯的基础**：`users.dingtalk_id` 存钉钉 userId，审计日志即可追溯到人。

**落地时的三个坑**（不做会**静默错位** —— 不报错，只是人力偏差算歪）：

1. 钉钉部门名可能带全角空格/不可见字符，比对前要清洗
2. 按**叶子部门**对，不按父部门对（`测试部-应用软件测试-云服务` 是叶子，`测试部` 是父）
3. 对不上的要写进对账报告，**不要静默忽略**
